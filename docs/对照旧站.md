# 对照笔记：旧站（你朋友那套） vs 你自己这套

这是我实际抓取、登录、核对过旧站之后的记录，用来对照学习。
左边是旧站真实行为，右边是 `peiwan-site` 里对应的实现位置。

---

## 一、接口对照

| 旧站接口 | 作用 | 我们这套的实现 |
|---|---|---|
| `GET /api/public` | 一次返回 `profile` + `slots`(168格) + `gallery` + `serverTime` | `app.py` → `do_GET` 里的 `/api/public` |
| `GET /api/availability?hours=1,2,3` | **只读**核对所选时间还在不在（不是提交！） | 同名同参数，逻辑一致 |
| **`POST /api/book`（旧站没有）** | 客户点一下就**锁定**时间并给你发通知 | 我们自己加的，见下面第四节 |
| `POST /api/auth` | 输密码换一个会话 Cookie | 同名；Cookie 名我们叫 `peiwan_session` |
| `GET /api/auth` | 查登录态 `{authenticated: bool}` | 一致 |
| `DELETE /api/auth` | 退出登录 | 一致 |
| `GET /api/admin` | 后台一次性拿全部数据 | 一致（多了 `notifyChannel` / `notifyTarget` / `notifyLast`） |
| `POST /api/admin/schedule` | `save-lock` / `save-batch` / `remove-lock` / `save-rule` / `toggle-rule / remove-rule` | 动作名全部一致 |
| **`POST /api/admin/notify` / `notify-test`（旧站没有）** | 保存通知渠道、发测试通知 | 我们自己加的 |
| `PUT /api/admin/profile` | 存资料，带 `revision` 防覆盖 | 一致（冲突返回 409） |
| `POST /api/admin/gallery` | 新增展示（旧站用 multipart 表单上传） | 我们用 JSON + base64（前端 canvas 先压缩） |
| `PATCH /api/admin/gallery` | 改公开/归档/标题 | 一致 |
| `POST /api/admin/password` | 改密码 | 一致（改完所有会话失效） |
| `GET /api/admin/export` | 导出业务备份 | 一致（下载 JSON） |
| `GET /api/media/<key>` | 存/取展示墙图片 | 一致，图片落在 `data/uploads/` |

> 你在旧站前台能看到的每一个功能，我们这套都有；接口命名我故意保持一致，方便你以后两边对照。

## 二、数据结构对照

```text
旧站 lock                           我们这套 locks 表
{ id, kind, start, end, client, note }       id/kind/start/end/client/note 完全一致
   kind = 'booking' 预约 / 'rest' 休息
                                    我们**多 6 个字段**（客户自助预约要用）：
                                      source       owner=自己锁的 / client=客户自助预约
                                      mode         模式名
                                      price        这一段总价（元）
                                      contact      客户联系方式
                                      contact_type wechat / xianyu / qq
                                      created_at   下单时间（毫秒时间戳）
                                    老数据库升级上来时由 ensure_column() 自动补上，
                                    老记录一条都不会丢（source 默认 'owner'）

旧站 rule                           我们这套 rules 表
{ id, days:[0..6], startHour, endHour,       一致（我们是 snake_case：
  from, until, note, enabled }                start_hour / from_ts / until_ts）
   0 = 周日；可跨午夜（22→6）；enabled=false 表示暂停

旧站 gallery                        我们这套 gallery 表
{ id, title, caption, category,              完全一致
  image, visible, archived, createdAt }
   category = 'screenshot' 截图 / 'review' 老板评价

旧站 profile（14 个字段）+ profileRevision   与我们 DEFAULT_PROFILE 一致
{ name, tagline, headline, bio, experience, wechat, xianyu, avatar,
  platform, accepting, announcement, styles[], prices[], promises[] }

旧站没有的那块：通知配置存在 store 表里
  notify_channel  off / pushplus / serverchan / webhook
  notify_target   token 或 webhook 网址
  notify_last     上一次发送结果 JSON {ok, time, detail}
```

## 三、时间格子的 5 种状态（两边名字对照）

| 我们代码里 | 旧站前台显示 | 我们前台显示 | 含义 |
|---|---|---|---|
| `free` | 可预约 | 可预约 | 空着，能点 |
| `booking` | 已预约 | 已预约 | 被你锁定的单 |
| `rest` | 休息 / 不接单 | 休息 | 命中固定休息规则或被手动设休息 |
| `past` | 已过去 | 已过去 | 这个小时已经过去 |
| `closed` | 暂停接单 / 停接 | 停接 | 你关掉了「开放接单」总开关 |

判断优先级（两边一样）：**过去 → 手动锁定 → 固定规则 → 总开关 → 空闲**。
代码在 `app.py` 的 `slot_status()`，一共 12 行。

## 四、预约流程（**这里和旧站不一样了**）

**旧站**（也是我们原来的做法）：

```
客户在主页点选格子
      ↓
点「下一步：选择模式」→ 前端先调 /api/availability 复查一遍（防止被人抢先）
      ↓
选模式 → 前端拼出一段微信文案
      ↓
客户复制文案 → 发到你的微信/闲鱼
      ↓
你在后台把那几格锁定成「预约」→ 别人就点不动了
```

**我们现在这套**（多了一条"点了就锁"的主路径）：

```
客户在主页点选格子
      ↓
点「下一步：选择模式」→ 前端先调 /api/availability 复查一遍（防止被人抢先）
      ↓
选模式 + 填联系方式（微信 / 闲鱼 / QQ）→ 点「立即锁定时间」
      ↓
后端 POST /api/book：在写锁里再复查一次空档
      ↓
连续的小时合并成段 → 每段一条 source='client' 的锁（模式/价格/联系方式/下单时间一起存）
      ↓
客户看到成功页（锁了哪几段、总价、可复制文案）
你手机上收到一条通知 → 加微信确认
```

- **两条路并存**：弹窗里那个「只复制文案，不锁定」还留着，适合"先问清楚再下单"的客户，
  文案里会写明"时间还没锁定"；
- **取消仍然是你说了算**：后台点那条记录的「取消」，格子立刻回到可预约；
  列表上「客户自助预约」和「自己锁定」用不同颜色的徽章区分；
- **两边都还是不接支付**：网站只负责"锁时间 + 通知你"，成交永远在微信里完成。

## 五、技术栈差异（不影响功能，影响你学起来的难度）

| | 旧站 | 你自己这套 |
|---|---|---|
| 后端 | Next.js 的 Route Handlers（Node.js） | Python 标准库 `http.server`（0 依赖） |
| 前端 | React + 服务端渲染 + 构建打包 | 原生 HTML + CSS + JS，**打开就是全部代码** |
| 数据库 | 未知（提供 JSON 导出，疑似文件/JSON 存储） | SQLite 单文件，随时能拷走 |
| 图片 | 上传后存 `/api/media/<uuid>`，前端压缩到 WebP | 一样（`canvas` 压缩到 1600px WebP） |
| 部署 | Render 免费实例 | 一样，`render.yaml` 都写好了 |
| 代码量 | 前端打包产物 400 KB+（读不动） | 6 个文件，全中文注释 |

## 六、旧站有、我们暂时没做的（想加我再带你加）

1. **首页动效开关**（右下角 `动效 ON/OFF`）——纯前端小功能，20 行能加。
2. **展示墙的分类筛选按钮**（全部 / 游戏截图 / 老板评价）——我们其实已经做了。
3. **"今日预约"统计卡**——我们做了，在后台第一屏。
4. **头像上传**——我们的资料里有 `avatar` 字段，但没做上传界面，可以先填图片网址。

## 七、我们比旧站多的 / 可以做得更好的

1. **数据不会因为改代码而丢备份**：我们有明确的 SQLite 文件 + 一键导出，`data/` 拷走就能迁移。
2. **密码用 PBKDF2 加盐哈希**存库，数据库被人拿到也看不到明文。
3. **版本号冲突保护**：手机上改一半、电脑上又改，第二个保存会被拦下来提示刷新（旧站也有，但我们注释写清楚了原理）。
4. **客户自助预约（旧站没有）**：`POST /api/book` 点了就锁，带限流（同 IP 10 分钟 5 次）
   和 6 小时上限；锁之前会在写锁里复查空档，两个人抢同一格只会有一个成功（另一个收到 409）。
5. **预约通知（旧站没有）**：PushPlus / Server酱 / Webhook 三选一，
   发送丢在后台线程里，客户不用等；成功失败都记在 `notify_last`，后台直接看原因。
6. **老数据库自动迁移（旧站没有）**：`ensure_column()` 让升级不影响已有数据。
7. **可选的下一步升级**：
   - 客户提交预约后先存成 `pending`，后台看到"申请列表"再一键转预约（更保守的做法）
   - 加"本月接了多少小时、收入多少"的统计（`locks` 里已经有 `price` 和 `created_at`）
   - 加第二种通知方式（照着 `send_notify()` 抄一支）

## 八、你可以照着做的练习

1. 打开 `app.py`，把 `DAYS_SHOWN = 7` 改成 `14`，重启，看时间表变成两周。
2. 把 `slot_status()` 里的顺序调一下（比如把 `closed` 判断提到 `rules` 前面），观察主页变化——**这就是在学"业务规则怎么变成代码"**。
3. 打开浏览器 F12 → Network，在主页点几个格子，先看 `/api/availability`，再点「立即锁定时间」看 `POST /api/book` 的请求和响应。
4. 把 `MAX_BOOK_HOURS` 从 6 改成 2，重启，试试一次约 3 小时会被怎么拒绝（顺便看 `static/site.js` 里的 `MAX_HOURS` 要一起改）。
5. 在后台锁一格，然后 `git diff` 你的 `data/site.db`（二进制，看不出变化是正常的：数据在库里，不在代码里）。
