## 四、必须知道的坑（踩过一遍了）

1. **`wsgi.py` 里必须调用 `site.init_db()`** —— `app.py` 的 `main()` 只在"直接运行"时执行，
   WSGI 模式不会执行，少了这一行，**所有读数据库的页面（含主页）都会 500**，而 `/api/ping` 正常。
2. **改 `app.py` 会让 `docs/代码导读.md` 的行号漂移** —— `tools/check_docs.py` 会报 `[漂移]`，
   按提示把行号改对即可（这个校验器就是为此存在的，别绕过它）。
   ⚠️ 它还会核对 ```python 代码块里的每一行代码是否真的存在于 `app.py`：
   讲概念用的**示意片段请用 ```text 围栏**，别用 ```python。
3. **文档里引用的「」UI 文案也被校验** —— 改前台按钮文字，要同步改文档。
4. **改数据库表结构必须用 `ensure_column()`** —— 老库已经存在，`CREATE TABLE IF NOT EXISTS`
   不会加字段；直接改 SCHEMA 会导致线上老库缺列报错。迁移要幂等、不能丢老数据。
5. **零第三方依赖** —— 只能用 Python 标准库（`urllib`/`sqlite3`/`http.server`…），
   不要引入 `requests`、`flask`…（PythonAnywhere 免费版也不让随便装）。
   **唯一的例外是 PIL**，而且只用于"从首屏图自动提取主色"，`import` 失败必须优雅降级
   （见 `extract_dominant_color()`）。
6. **写文件不要用 PowerShell 的 `Set-Content -Encoding UTF8`** —— 会加 BOM，破坏 Python 解析。
7. **PythonAnywhere 出网有白名单** —— 别随便加"调用某个 API"的功能，先查
   <https://www.pythonanywhere.com/whitelist/>（PushPlus / Server酱 / 飞书 / 钉钉 / ntfy 在里面）。

### ★ 分区相关的坑（这一版新踩的）

8. **时间表绝对不能按分区隔离** —— `build_slots()` 不接 zone 参数，`locks` 表的 `zone`
   只是"这单从哪个招牌来的"标记。谁要是"顺手"给每个分区各存一套时间，客户就会撞单。
   `tests\test_zones.py` 第 2 节有一条断言守着它（任意分区的 slots 必须完全相同）。
9. **分区资料的价格是"自由文本"** —— `priceGroups[].items[].price` 里是 `"20R/月"`、`"推图15R"`
   这种人类写法，**不要自动转成数字或 ¥**。只有预约制分区的 `prices[].price` 是数字。
10. **保存分区资料是"部分更新"**（`save_zone_profile()`）—— 没传的字段保留原值。
    前端"批量导入价目表"就是靠这个只发 `priceGroups`。
    想清空字段要显式传 `""`。
11. **分区资料整体存在 `zones.profile` 这一个 JSON 字段里** —— 加字段要同时改
    `DEFAULT_ZONE_PROFILE` 和 `ZONE_TEXT_KEYS`（白名单），否则保存时会被清洗掉。
12. **隐藏 ≠ 删除**：`visible=0` 的分区不出现在首页/导航，但 `/z/<id>` 和
    `/api/public?zone=<id>` **仍然照常工作**（已经发出去的链接不能失效）。
    真删要 `confirm:true`，而且只删分区本身：展示墙图片和预约记录会变成"未分区"，不会被删。
13. **`/z/<id>` 的路由放在 `/nya-0508`、`/static`、`/api` 之后** —— 这样分区 id 永远抢不走
    后台和接口的网址。加新页面时注意别把 `/z/` 判断挪到前面去。
14. **迁移只做一次**：`migrate_to_zones()` 靠 `store` 里的 `zones_migrated` 标记 +
    "zones 表已有数据就跳过"两道保险。改这个函数时**别删这两道保险**，
    否则老库每次启动都会多建一个 delta。

### ★ 客户档案相关的坑（这一版新踩的）

15. **"今天"必须是北京时间的今天**（`today_cn()`）—— 免费服务器跑在 UTC 上，
    直接 `datetime.now()` 会比北京时间晚 8 小时：北京时间早上 7 点时，"今天到期"的客户
    会被算成"还有 1 天"，**该催的那天就不催了**，续费也会整体差一天。
    改动这一块之后，`tests\test_customers.py` 第 4 节会用 `TZ=UTC / America/New_York /
    Asia/Tokyo` 三个子进程验一遍。
16. **客户金额（`price`）和分区价目表一样是自由文本** —— `"20R/月"`、`"推图15R"`、
    `"100R/月（含月卡5R）"`，**永远不要自动加 ¥、不要转成数字**。
17. **`daysLeft` 和 `level` 由后端算好一起返回**，前端只负责显示和上色。
    别在前端"顺手再算一遍日期" —— 迟早会出现"后端说超期、前端说还有 1 天"。
    （唯一的例外是续费弹窗里那个**预览**，它必须和后端 `add_months()` 用同一套算法：
    JS 的 `setUTCMonth()` 遇到 1 月 31 日 + 1 个月会滚到 3 月 3 日，
    和后端的"压到 2 月 28 日"对不上，弹窗就会骗人。）
18. **`end_date` 留空 = 长期/一次性，永远不进待催列表** —— 这是故意的，不是 bug。
    一次性单子和长期老板不该天天出现在催收清单里。
19. **已超期的客户用 `extend` 续费，算出来的日期可能还是过去的**（"补上空窗"）。
    后端在这种情况下会回一个 `tip` 让后台提示改用「从今天算」——别把这段提示删了。
20. **老备份里没有 `customers` 字段 → `apply_backup()` 必须整段跳过**（`has_customers`），
    否则主人辛苦录的客户会被一份老备份清空。这条有断言守着。

### ★ 「第一刀 / 第二刀」踩到的坑（2026-10-13 加的）

21. **★ `_db_lock` 是普通的 `Lock`，不是 `RLock` —— 在它里面再调用会写库的函数 = 直接死锁。**
    我真踩了：`admin_schedule` 的 `set-auto-release` 分支里调了 `set_auto_release_hours()`，
    而它内部走 `set_store()`，`set_store()` 自己也要拿 `_db_lock` —— 结果是**整个网站卡住，
    任何请求都不再响应**（日志停在那一行，没有异常）。自检跑到第六阶段才发现。
    **规矩**：`with _db_lock` 里面只做 `conn.execute(...)`；
    要调用别的写库函数（`set_store` / `set_categories` / `set_gallery_categories` / `list_*`），
    一律挪到 `with` **外面**。加代码之前先问一句："这个函数会不会回头写库？"
22. **展示墙分类"有图在用就不许删"，是**故意的**，不是没做完。** 我选的取舍是
    **不自动把图搬到别的分类**（`admin_gallery_categories` 里有完整理由）：那会悄悄改变
    客户看到的分组，而主人不会意识到自己刚才那一下动了什么。错误信息里写了"还剩几张图"。
    空分类随便删。
23. **展示墙分类的 `id` 不许改，只许改名。** 老图的 `category` 字段存的就是 id。
    后台那行的 id 是只读显示 + 一句"（不可改）"。
24. **`clean_link()` 的协议白名单是安全底线**：展示墙的链接会变成 `<a href>`，
    只认 `http://` / `https://`，`javascript:` / `data:` 一律洗成空字符串。
    **前端那道校验只是省事，后端这道才是防线**（前端永远可以被绕过）。
25. **`locks.confirmed` 的默认值必须是 1。** 老库里的锁全是主人自己弄的，升级时不该
    集体变成"待确认"。只有**新提交的**客户自助预约才写 `confirmed=0`（`create_booking`）。
    同理 `apply_backup()` 里老备份（没有 `confirmed` 字段）恢复成"已确认"。
26. **自动释放是"惰性清理"，靠 `/api/public` 和 `/api/admin` 顺手做**，没有定时任务
    （免费托管没有常驻定时器）。所以它是**"下一次有人访问时才生效"**，不是掐着秒表执行的 ——
    跟主人解释的时候要说清这一句，不然他会以为"到点了没删"是 bug。
    四道安全阀里最要紧的是**只删 `start > now` 的**（已经打过的不碰）。
27. **自动释放默认 0 = 关闭，这是主人的明确要求。** 悄悄删掉客户占的时间不能替他做主
    （客户可能是半夜下的单）。测试里"关闭时什么都不删"和"开了才删"都要有断言。
28. **给测试用的两个口子别当成正式功能**：`app.backdate_lock()`（把锁的下单时间往前拨）
    和 `AUTO_RELEASE_CHECK_SECONDS` 环境变量（把 30 秒节流关掉）。
    自检脚本会把后者设成 0，否则 5 种边界没法在几秒内连着验。
29. **`/api/book` 有"同一 IP 10 分钟最多 5 次"的限流** —— 写测试时如果一路 `book()` 下去，
    第 6 次开始全是 429，后面的断言会莫名其妙地"找不到那条锁"。
    `tests\test_confirm.py` 里的做法是：**只约 4 次，其余场景直接往库里造锁**
    （`make_client_lock()`），这样想验哪条边界就造哪条。
    （`tests\test_income.py` 也用了同一招：要一条"price=45 的待确认预约"就直接 INSERT。）

### ★ 「第三刀」踩到的坑（2026-10-13 加的，收入登记 + 月度统计）

30. **★ 记账钩子必须写在 `with _db_lock` 的「外面」（这是坑 21 的第二次踩）。**
    `confirm-lock` 那个分支里原来只有一句 UPDATE，我顺手在它下面加了
    `record_booking_payment(row)` —— 而 `record_payment()` 内部要 `with _db_lock` 去插流水。
    普通 `Lock` 不可重入，**那就等于全站卡死**。
    正确的写法（现在代码里就是这样）：锁里只把那条锁**查出来存进变量**
    （`confirmed_lock = dict(row)`），`with` 结束之后再记账。
    **检查清单：任何新加进 `admin_schedule` / `admin_payments` / `admin_customers`
    的调用，先问一句"这个函数会不会回头写库？"**
31. **★ `record_payment()` 返回的必须是 `income_view()` 洗过的字典，不是数据库那一行。**
    我第一版写的是 `return get_payment(pid), "已记一笔"`，而调用方要拼一句
    `"已记一笔收入 %s %s" % (payment["amountText"], payment["label"])` ——
    `amountText` / `label` / `sourceLabel` 这些都是 `income_view()` 才加的字段，
    于是 `KeyError: 'amountText'`，**确认预约的接口直接 500**（自检当场报出来了）。
    原文见 `tests\test_income.py` 的输出：`KeyError: 'amountText'`。
32. **★ 给 `payments` 加字段时，`insert_payment()` 和 `apply_backup()` 里那两条 SQL 要一起改。**
    这就是坑 21 的"备份两端要同步"在收入这一刀上的翻版：
    两处的列名和 `?` 个数必须完全一致，少改一边 = 恢复备份时 `ProgrammingError`
    （而且前面的阶段可能全是绿的，很晚才发现）。
33. **收入流水的日期是"字符串 'YYYY-MM-DD'"，不是毫秒时间戳** ——
    和 `locks.start`（毫秒）、`customers.end_date`（也是字符串）摆在一起最容易混。
    字符串的好处是**字典序 = 日期序**，`date >= start and date <= end` 直接就能比大小，
    不用把每一行都转成时间戳（几千行流水会慢得能感觉出来）。
    需要在日期上做加减时用 `add_days_text()` / `add_months_text()`，别自己拼字符串。
34. **"上月没有记录"时 `momPercent` 必须是 `None`，界面说人话，绝不显示 0%。**
    0% 的意思是"和上月一样"，而"上月一笔都没有"是另一件事 —— 显示 0% 就是骗他。
    前端也是按 `momPercent === null` 判断要不要上色（`renderIncome()`）。
35. **老备份（没有 `payments` 字段）导入时，收入流水必须一条都不动**（`has_payments`）。
    道理和 `has_customers` 一样，但**这一条更严重**：客户档案还能靠"重新问一遍"补回来，
    而收入流水是算出来的 —— 手动补记的那几笔（剪辑 / PS / 建站）连单据都没有，
    恢复时清空一次就**永远补不回来了**。`tests\test_income.py` 第 15.2 节守着它。
36. **"本月"的口径 = 北京时间**（`income_range_bounds()` + `today_cn()`），
    和客户到期那一套完全一致。服务器在 UTC 时，北京时间 10 月 1 日早上 7 点还是"9 月"，
    一整个月的账都会算错。测试里用 `TZ=UTC / America/New_York / Asia/Tokyo` 三个子进程验。
37. **今日待办条上故意「没有」收入数字**（主人明确要求的取舍）。
    那是"今天要干什么"，不是"这个月赚了多少"。混在一行里，他扫一眼就分不清
    "3 单要打"和"¥1240"哪个是待办、哪个是结果。钱的事只在「收入」标签页看。

### ★ 「第四刀」踩到的坑（2026-10-15 加的，文案可改 + 服务条款 + 图片显示位置）

38. **★ 文案只存"和默认不一样"的那几句**（`clean_texts()`）。规矩是：
    空字符串 = 用默认，填得和默认一字不差也**不存**。为什么后者也要丢：
    后台的输入框里预填的是"现在生效的那句"，要是原样存下来，主人只是点开看一眼再保存，
    80 多句就全被"钉死"成今天这版默认值了 —— 以后默认文案改好了他反而收不到。
    **代价**：保存接口是"整页覆盖"语义（后台每次发全部 80 多格），写测试时要注意
    （`tests\test_texts.py` 里那个 `OVERRIDES` 字典就是为此存在的，第一版我就踩了）。
39. **文案一律当纯文本渲染，不认 HTML**（前台 `textContent`，后端 `escape_html`）。
    这是**安全底线**：文案是后台输入框里编辑、存进数据库、再由服务端拼进页面的 ——
    允许标签就等于给"任何拿到后台的人"开了一个往客户页面塞 `<script>` 的口子
    （而主人是要把后台地址存进手机书签的）。代价是几条 `<b>` 没了，值得。
    同理，条款正文里的换行是**我们自己拼** `<p>` / `<br>` 的，不是让主人写 HTML。
40. **`{name}` / `{zone}` / `{max}` / `{wechat}` 是"文案里的变量"**：前三个由前台
    `tx()` 替换（`site.js` / `zone.js` 各一份），`{wechat}` 由后端 `terms_fill_vars()` 替换
    （条款页是服务端渲染的）。改文案时把占位符删掉，那句话就和实际规则对不上了
    （比如"一次最多 {max} 小时"变成死数字）。
41. **★ `site_summary()` 里那两个嵌套对象不能放在最后**：`texts` 和 `imagePositions`
    都是 dict，如果它们是 `site` 的最后一个键，`json.dumps` 出来的 `__PAGE__` 里会出现
    `}}` —— 而 `tests\test_zones.py` 有一条老断言在查"首页 HTML 里不该有 `{{` / `}}` 残留"
    （它防的是模板占位符漏渲染）。**这条断言不许为了过测改掉**，所以把嵌套对象放在
    中间（后面跟一个字符串字段）就永远不会撞上。加字段时留意这一点。
42. **图片「显示位置」跟着图片走，不另开 store key**：首页那三张存在全局资料
    （`avatarPosition` / `backgroundPosition` / `heroImagePosition`），分区那两张存在
    `zones.profile`（`backgroundPosition` / `heroImagePosition`）。好处是"保存主页设置 /
    保存这个分区"顺手就存了、备份一个字都不用改（profile 整个都在备份里）。
    **读的时候统一过 `clean_image_position()`**，所以库里存了脏值最坏也只是退回 `center`
    （= 这一版之前的行为），绝不会把奇怪的字符串塞进 CSS。
43. **位置字段要在 `ZONE_TEXT_KEYS` 的白名单循环之外单独处理**：`ZONE_TEXT_KEYS` 只做
    "截断"，而位置要按 9 个合法值**校验**。混在一起写会让 `"left top"` 之类被当普通文本。
44. **`/terms` 是服务端渲染、故意不用 JS**：客户不装 JS 也能看全，微信抓分享卡片、
    搜索引擎爬到的都是完整内容。所以它**不接入 site.js / zone.js**，
    也不受"JS 渲染"那一套影响；代价是 `templates/terms.html` 里的占位符要自己拼
    （`serve_terms()` 里那张 payload 表），**加了新的 `{{X}}` 一定要记得在
    `safe` 那三个例外里挑对**：`{{WECHAT_LINE}}` / `{{TERMS_SECTIONS}}` 是我们自己拼的
    HTML，忘了放进例外，客户就会在页面上看到一串源码（截图里真抓到过一次）。
45. **服务条款的"最后更新"日期由服务器写**（`save_terms()` 里 `today_cn()`），
    不让前端传、也不给输入框 —— 手填的日期百分之百会忘记改。
    恢复备份时允许带一个明确日期进来（那是"还原成备份那天的样子"）。
46. **`_shots2/`（截图目录）里的东西不进包**：`tools\make_package.py` 和
    `tools\check_deploy_ready.py` 的 `SKIP_DIRS` 里都有它，`.gitignore` 里也有。
    截图脚本用的是 `%TEMP%\peiwan-shots-data` 这个独立数据目录，**不碰 `data/`**。
47. **★ 别用 PowerShell 的 `Get-Content -Raw` + `WriteAllText` 改这些文件**（我真踩了）：
    这个 shell 把 UTF-8 文件按 GBK 读进来再写回去，`docs\代码导读.md` 当场变成一片乱码，
    最后是从 `peiwan-site-上传用.zip` 里把它捞回来的（那次 zip 正好是改之前的）。
    **规矩：改文件只用编辑工具或 Python 的 `io.open(..., encoding="utf-8", newline="\n")`。**
    （这条是"坑 6"的加强版：不只是 BOM 的问题，读进来那一刻就已经坏了。）
48. **截图里的"滚动"要先把平滑滚动关掉**：`style.css` 里有 `html{scroll-behavior:smooth}`，
    JS 里 `scrollTo` 会变成一段动画，headless Chrome 在动画跑完之前就截图了
    （表现是 scrollY 一直是 0）。截图脚本里要先 `documentElement.style.scrollBehavior='auto'`。

| 限流按"提交次数"算 | 参数写错也算一次；改 `book_rate_limited()` 可调 |
| 没有订单状态机 | 客户预约即锁定，主人手动取消（这是主人指定的流程） |
| **分区删除后展示墙图片变"未分区"** | 故意不删图（怕误删）；后台列表仍能看到，可以改挂到别的分区 |
| 服务制分区的"起步价"：带「月」的优先，再取数字最小的 | 文本价格没法可靠比大小；规则写在 `zone_start_price()` 的注释里，`tests\test_zones.py` 有 3 条断言守着 |
| 分区的 `theme` 只在分区页生效 | 首页用默认主色（首页是"个人品牌"，不做成花的） |
| 模板默认资料是"示例名字 / your_wechat_id / Nya" | 故意中性化，避免公开仓库带个人信息 |
| ★ **展示墙分类"有图在用就不许删"**（不自动把图搬家） | 我选的。自动搬家会悄悄改变客户看到的分组，主人不会察觉；宁可让他手动挪（坑 22） |
| ★ **自动释放是"下一次有人访问才生效"** | 免费托管没有常驻定时器，所以是惰性清理；跟主人解释时要说清这一点 |
| ★ **自动释放默认关（0）** | 主人的明确要求：悄悄删客户占的时间不能替他做主 |
| ★ **释放时段不通知客户** | 后台弹窗里提醒主人"客户那边不会收到通知，建议先微信问一句" |
| ★ **前台展示墙一次只显示一个分区的图**（老规矩） | 展示墙从一开始就是"按分区隔离"的，链接/分类没有改变这一点 |
| ★ **收入流水里不记 0 元** | 我选的：`price=0` 的预约确认后不记账、手动记账 0 元直接 400。流水里一堆 ¥0 会把"这个月收了多少"搞浑，也会让排行全是 0（那是噪声，不是信息） |
| ★ **"未分类"是收入页上一个正常的大类** | 没挂分区（或者分区被删了）的记录归到它。**它不是错误，是个有用的信号**：说明有单子没挂在任何分区上（剪辑 / PS / 这类一次性单子多半就在这儿） |
| ★ **时间范围是"自然月"口径，闭区间** | 本月 = 本月 1 号 ~ 本月最后一天（最后一天 = 下月 1 号 - 1 天）；环比比的是**上一个自然月**，不是"上一个等长区间"。理由：他想的是"这个月比上个月怎么样" |
| ★ **上月没记录时不显示环比百分比** | 说「上月没有记录」。显示 0% 是骗人 —— "从无到有"和"没变化"是两件事 |
| ★ **续费填的金额按"今天"记，确认预约按"这单开始那天"记** | 两个日期口径**故意不同**：续费是"今天收了钱"，预约是"这单发生在哪天"（他多半是打完之后才点确认的，跨月时按开始那天算才对） |
| ★ **收入的备注里写明了是自动记的** | 比如「确认预约自动记账」「续费自动记账（2026-10-20 → 2026-11-20）」。日后对账时他能一眼看出来源，而不是怀疑系统乱记 |
| ★ **文案故意不支持 HTML**（只能写纯文本） | 见坑 39：允许标签就等于给"任何拿到后台的人"开了往客户页面塞 `<script>` 的口子。代价是几条 `<b>` 没了，用 CSS 补 |
| ★ **不改的那几类字**：关闭 / 取消 / 清空 / 刷新这类纯功能小按钮、"已选时间 / 小时"这种数字+单位标签、以及"这些时间已不可约：10月15日 20:00"这种**由数据拼出来的句子** | 前者改了没有信息价值还容易改出病句；后者不是"一句话"而是"数据 + 文案"，要支持它得引入模板语法，收益很低。**想改哪句偏偏不在目录里，加一行就行**（`TEXT_GROUPS`） |
| ★ **展示墙的图不给"显示位置"** | 它是 170px 高的缩略图、一批图共用一套样式（`.gallery-item img`）；单张控制要给它加一列字段 + 每项一个界面。**要做的话**：`gallery` 加 `pos` 列（`ensure_column`）+ `insert`/`apply_backup` 两处 SQL 同步（坑 32）+ 后台每项一个下拉 + `zone.js` 写 `object-position` |
| ★ **`/terms` 不接 JS、也不进 check_frontend 的"配对"表** | 它是服务端渲染的静态页；`tests\check_frontend.js` 只检查"有 JS 的页面"，但它的 class 参与"CSS 类有没有被用"那一项（所以 `terms.html` 在 `htmlAll` 里） |
| ★ **截图（`_shots2/`）不进包、也不提交** | `.gitignore` 和两个 `SKIP_DIRS` 里都排掉了；截图脚本用独立临时数据目录，不碰 `data/` |

### 15. 前端"排队中"的字段，保存时必须一起提交（真踩过）

分区图标曾经传完后刷新就没了：上传时代码把图存进了内存（`z.icon = url`），
但点保存时发的 payload 里**只有 name / short / theme，漏了 icon** —— 图就永远存不进去。

**教训**：凡是"先改内存、后点保存"的字段，都要确认 `collectXxxForm()` 和保存函数里
**两端都带上它**。加新字段时的检查清单：
1. 上传/输入时有没有写进 state？
2. `collectXxxForm()` 有没有把它收集进去？
3. 保存接口有没有把它发给后端？
4. 后端白名单里有没有它？
5. 刷新后 `fillXxxForm()` 有没有把它读回来？

### 16. CSS 的 `img { display: block }` 会盖掉 `hidden` 属性

没上传微信二维码时，页面上出现一个空白方块 —— 因为 `<img hidden>` 被
`img{display:block}` 覆盖了，`hidden` 属性失效。

**已经修好**：`style.css` 第 46 行有一条全局兜底
```css
[hidden] { display: none !important; }
```
以后动态隐藏元素，直接设 `.hidden = true` 就行，不用担心被 CSS 盖掉。

### 17. 表格类布局在手机上要单独看

价目表三列（名称/价格/说明）在 390px 手机上，名称列被挤成"一字一行"。
**已经修好**：手机上收窄内边距 + 名称列 `white-space: nowrap`。

**教训**：任何多列布局（表格、grid）改完，都要在手机宽度下看一眼；
`tests/check_frontend.js` 查不出这种问题，只能靠真人看。

### 18. 校验器扫不到的"动态 id"，放回 HTML 里（template 比字符串拼接好）

后台展示墙的「展开编辑」小块（改分类 / 改外链）一开始是我在 JS 里拼字符串生成的，
`tests/check_frontend.js` 立刻报 `geCategory / geLink / geState 在 admin.html 中缺失` ——
因为那个校验器只扫 `.html` 文件，认不出模板字符串里拼出来的 id。

**改法**：把那一小块写成 `templates/admin.html` 里的 `<template id="galleryEditTemplate">`，
JS 用 `tpl.content.firstElementChild.cloneNode(true)` 克隆一份。
好处不只是"校验器过了"：**那块 HTML 从此有了一个能被检查的家**，
以后谁把 `id="geLink"` 打成 `id="gLink"`，跑一下校验就报出来。

> 想在注释里"骗过"校验器（写一行 `id="geLink"` 的字面量）也能过，
> 但那是自欺欺人 —— 校验器过了，代码还是没人管。**能放回模板的就放回模板。**
