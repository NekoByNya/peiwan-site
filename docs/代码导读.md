# 代码导读：这个网站到底是怎么跑起来的

这份文档的目标只有一个：**让你打开 `app.py` 不再发懵**。

读法建议：不用从头读到尾。先看下面的"全景图"，然后挑你最想改的那一节看。
行号是我写这份文档时从真实文件里提取的，**你改过代码之后行号会变，以函数名为准**
（`python tools\check_docs.py` 会自动帮你核对）。

## 一、全景图：客户打开一次网页，发生了什么

```
客户手机（微信里点开链接）
   │
   │ 1. 请求 https://你的域名/          或者  /z/delta（某个分区页）
   ▼
┌────────────────────────────────────────────────────────────┐
│  app.py（在 PythonAnywhere / Render 上跑着）                │
│                                                            │
│  do_GET()  ← 所有读请求都从这里进（第 3837 行）              │
│     ├─ "/"           → render_page("index.html")  个人主页  │
│     ├─ "/z/<分区id>"  → render_page("zone.html", 分区)       │
│     ├─ "/static/…"   → 直接发文件                           │
│     └─ "/api/public" → public_payload() 现算 168 格 + 分区   │
│                          ├─ build_slots() 生成时间表        │
│                          └─ zone_public_view() 拼分区资料    │
│                                                            │
│  do_POST() ← 客户点「立即锁定时间」走这里（第 3984 行）       │
│     └─ "/api/book"  → api_book() → create_booking() 立刻锁定 │
│                          └→ notify_owner() 推给你            │
└──────────────┬─────────────────────────────────────────────┘
               │ 2. 读/写
               ▼
        data/site.db（SQLite 文件）
        ├─ store     全局资料、大类列表、密码、上次导出时间、通知配置
        ├─ zones     ★ 分区（三角洲 / 守望 / 明日方舟…），每个分区一份 profile
        ├─ locks     被锁定的时段（预约 / 休息）—— **全局共用，不按分区隔离**
        ├─ rules     固定休息规则
        ├─ gallery   展示墙（每条都带 zone，说明它属于哪个分区）
        ├─ customers ★ 客户档案（谁哪天到期、买了什么档位、多少钱）
        └─ payments  ★ 收入流水（★ 全站唯一"金额必须是数字"的地方）
               │
               │ 3. 返回 JSON
               ▼
客户浏览器里的 zone.js → 把 JSON 画成时间表 / 价目表
```

**一句话总结**：服务器**不保存页面**，每次请求都现场算一遍再发出去。
所以你改一条休息规则，整周时间表立刻跟着变；改一个分区的价格，那个分区页立刻跟着变。

## 三、两级分区是怎么回事（★ 最重要的一节）

### 1. 三个概念，一句话说完

| 概念 | 存在哪 | 例子 | 能不能删 |
|---|---|---|---|
| **大类** `categories` | `store` 表里的一段 JSON | 陪玩 / 代肝 / 其他服务 | ❌ 只能改名、改类型、排序 |
| **分区** `zones` | `zones` 表，一行一个 | 三角洲行动 / 守望先锋 / 明日方舟 | ✅ 能删（但要二次确认） |
| **分区资料** `zones.profile` | 就是分区那一行的 `profile` 字段（JSON 文本） | 价格、标语、背景图、首屏图… | 跟着分区走 |

```
/                     个人主页：品牌 + 按大类分组的服务卡片 + 信任信号 + 加微信
/z/delta              三角洲陪玩   （陪玩类 → 有时间表）
/z/overwatch          守望先锋陪玩 （陪玩类 → 有时间表）
/z/arknights          明日方舟代肝 （服务类 → 只有价目表，没有时间表）
/z/editing            视频剪辑     （服务类 → 只有价目表）
```

**`kind` 决定长什么样，而不是"哪个页面"决定**：

```	ext
kind="booking" → 该大类下的分区显示预约时间表，用扁平 prices（三档数字价格）
kind="service" → 该大类下的分区**不显示时间表**，用分组价目表 priceGroups（价格是自由文本）
```

`kind` 存在**大类**上（`list_categories()`，第 1158 行），分区通过 `category` 字段挂到大类上。
所以你把"代肝"大类改成预约制，它下面所有分区会一起变成有时间表 —— 一个字段控制一片。

### 2. ★ 时间表是全局共用的（这条千万别改错）

```
   客户的视角                          数据库的真相
   ──────────                          ────────────
   守望分区页 → 选格子 → 锁定    ┐
                                 ├─→  locks 表（只有一份！）
   三角洲分区页 → 选格子 → 锁定  ┘     每条记录带一个 zone 字段
                                       只是"标记这单从哪来的"
```

- `locks` 表**没有**"按分区隔离"这回事：它只有 `zone` 一个标记字段（第 2414 行 `LOCK_COLUMNS`）；
- `build_slots()`（第 3656 行）算格子时**完全不看 zone** —— 所以 `GET /api/public?zone=X`
  不管 X 是什么，返回的 168 格永远一模一样（`tests\test_zones.py` 里有这一条断言）；
- 为什么这样设计：**主人只有一份时间**。如果每个分区各锁一套时间，守望的客户和三角洲的客户
  可以同时约到晚上 8 点 —— 那就出大事了。

### 3. 分区资料的字段（`DEFAULT_ZONE_PROFILE`，第 555 行）

```	ext
{
  "game": "守望先锋",            # 游戏名 / 服务名（预约文案用它）
  "tagline": "一句话简介",
  "headline": "首屏大标题（\n 换行）",
  "subheadline": "副标题",
  "bio": "详细介绍",
  "highlights": ["官服B服都接", "低练度也接"],   # 服务亮点（就是原来的 styles）
  "promises": ["服务承诺1", "服务承诺2"],
  "announcement": "该分区的公告",
  "platform": "PC 电脑端",
  "background": "",              # 该分区自己的背景图
  "heroImage": "",               # 该分区自己的首屏主视觉
  "shareImage": "",              # 该分区自己的微信分享缩略图（1200×630）
  "priceSheetImage": "",         # 价目表长图（服务型分区用）
  "backgroundDim": 72,           # 背景压暗程度
  "prices": [ … ],               # ★ 只有 booking 类分区用：三档数字价格
  "priceGroups": [ … ],          # ★ 只有 service 类分区用：分组价目表（价格是自由文本！）
  "featured": ["i1", "i2"],      # 「主推档位」：从 priceGroups 里挑的 item id（最多 3 个）
}
```

> ⚠️ **`priceGroups` 里的价格是"自由文本"**（`"20R/月"`、`"推图15R"`）。
> 后端一个字都不会改（`clean_zone_profile()` 第 1317 行只做截断和去空格）。
> 主人就是这么写的，别自作主张换成 `¥`。（客户档案里的金额也是同一个规矩。）

### 4. 起步价怎么算（`zone_start_price()`，第 905 行）

首页每张服务卡片右下角那行小字：

| 分区类型 | 规则 | 例子 |
|---|---|---|
| `booking` | 取 `prices` 里**最小的数字** | `¥15/小时起` |
| `service` | 价格是文本没法可靠比大小：**先挑带"月"的**（月付最常见），再按文本里第一个数字升序取最小的；一条"月"的都没有就按数字最小的取；文本里连数字都没有就取第一条 | `20R/月起` |

一条价格都没有 → 返回空字符串，卡片上就不显示这一行。
（这样"8R/周"这种更便宜但周期更短的项目不会抢戏，但只有按周报价时也会照实显示 `8R/周起`。）

### 5. ★ 老数据是怎么搬过来的（`migrate_to_zones()`，第 1901 行）

`init_db()` 每次启动都会调它，但它**只做一次**（靠 `store` 里的 `zones_migrated` 标记 +
"zones 表已经有数据就跳过"两道保险）。做完的事：

```
① 建 3 个默认大类（陪玩 / 代肝 / 其他服务）
② 用老的全局 profile 建出第一个分区 delta：
     老 game        → 分区名 + profile.game
     老 styles      → profile.highlights
     老 prices      → profile.prices
     老 promises    → profile.promises
     老 background / heroImage / backgroundDim / tagline / headline / bio /
        announcement / platform  → 原样搬进分区
③ 老 gallery 全部标记 zone='delta'
④ 老 locks  全部标记 zone='delta'
⑤ 全局 profile 只留跨分区共用的：
     brand / name / tagline / wechat / xianyu / avatar / bio / accepting / trust
     （老的 game / platform 继续留着 —— 老接口和老后台还在读它们）
```

**⚠️ 它只"添加"和"打标记"，从不删除任何一行数据。** 老的预约记录、展示墙一条都不动，
只是多了一个 `zone` 字段的值。`tests\test_zones.py` 的第 15 节专门造了一个"旧版数据库"
来验证这一点（含"再跑两次 init_db 也不会重复迁移"）。

### 6. 主题色是怎么注入页面的（`theme_style()`，第 4707 行）

每个分区可以有自己的主色（`zones.theme`，后台用取色器选）。样式表一行都不用改：

```html
<!-- app.py 在 HTML 里插一小段 <style>，覆盖 style.css 顶部的三个变量 -->
<style>:root{--accent:#8fa832;--accent-rgb:143, 168, 50;--accent-ink:#ffffff}</style>
```

| 变量 | 干什么用的 |
|---|---|
| `--accent` | 高亮色：按钮底色、边框、强调文字 |
| `--accent-rgb` | `"143, 168, 50"` 这种分量写法，给 `rgba(var(--accent-rgb), .3)` 用（CSS 没法直接把 `#rrggbb` 拆成三个数字，所以在服务端算好） |
| `--accent-ink` | 主色底上的文字颜色（按感知亮度自动选黑字或白字） |

颜色不合法（不是 `#rrggbb`）就返回空字符串，页面用默认主色，不会崩。

### 7. 微信分享卡片为什么每个分区不一样（`share_image_url()`，第 4667 行）

客户转发 **守望分区** 的链接，卡片上就该是守望的图：

```
分区页：分区 shareImage → 分区 heroImage → 该分区展示墙第一张公开图 → 全局头像 → 自带默认图
个人主页：全局头像 → 第一个可见分区的 heroImage → 该分区展示墙第一张 → 自带默认图
```

`og:title` 用「分区游戏名 · 你的昵称」，`og:url` 是 `/z/<分区id>`（都在 `render_page()` 第 4744 行里拼）。

### 8. 分区页的 HTML 是"一个模板两种长相"

`templates/zone.html` 里**预约制和服务制的两套区块都写着**，由 `zone.js` 按
`<body data-kind="booking|service">` 显示／隐藏（`renderPrices()` / `bindEvents()`）：

- 预约制：显示三档价格 + 时间表那一整块；服务制的那块 `hidden`；
- 服务制：显示主推档位 + 分组价目表；时间表那块 `hidden`，而且**时间表相关的事件不绑定**
  （元素不存在，绑了会报错）。

### 9. ★ 分区页的顺序 + 左侧导航 + 三块折叠（"第六刀"，2026-10-16）

**顺序**（电脑和手机一样，`templates/zone.html` 里从上到下的 section 就是它）：

```
首屏 → 档位(services，里面跟着服务流程 stepsPanel)
     → 须知(promises) → 预约(schedule) → 问答(faq) → 展示(gallery) → 页脚
```

两条"为什么"：

- **须知排在预约前面**：客户**下单之前**就该看到规则（以前在预约后面，等于下完单才告诉他）；
- **常见问题是独立的 `<section id="faq">`**：它的位置（预约后面）由它自己那一块决定，
  不再跟着"价格区"跑。`#faqPanel` 这个 id 保留着（里面装标题 + 列表）。
- **服务制分区**没有 `#schedule`（`hidden`），顺序自动变成 档位 → 流程 → 须知 → 问答 → 展示。

**左侧固定导航 `#zoneNav`**（只在分区页、只在 ≥1440px）：

| 关心的事 | 在哪 |
|---|---|
| 谁进导航 | `templates/zone.html` 里带 `data-nav="<文案 key>"` 的块（首屏、页脚故意不带） |
| 导航怎么生成 | `zone.js` 的 `renderNav()`：`$$('[data-nav]')` **按 DOM 顺序**收集 → 一个一个生成 `<a>` |
| 导航词 | `TEXT_GROUPS` 的 `navZone*` 六个键（后台「文案 → ② 分区页 · 价目」能改） |
| 点击跳转 | `scrollToNavBlock()`：`window.scrollTo({top, behavior:'smooth'})`，目标 y 减去 `navOffset()` |
| 高亮哪一项 | `updateActiveNav()`：块顶越过"吸顶导航下沿"的最靠下的那一块（滚到底就是最后一块） |
| 为什么被顶栏挡住 | `[data-nav] { scroll-margin-top: 78px; }`（吸顶导航 61px + 余量） |
| 为什么不挤压正文 | `@media (min-width: 1440px) { body { padding-left: 192px; } }` —— 占的是正文左边那块空地，`.container` 一个字没改 |

> ★★ **一条铁律：导航项绝不手写列表。** 主人专门点过："不能出现正常滑动是 A,B,C,D、
> 而导航栏顺序却是 A,C,D,B"。所以导航只认 `data-nav` + DOM 顺序 —— 以后挪块 / 加块 / 删块，
> 导航自动跟着变。`tests\test_faq_steps.py` 第 3b 节有断言守着"没有手写的导航项列表"。

**三块折叠**（原生 `<details>`，默认收起）：

| 块 | 折叠方式 | 摘要行右边那串字 |
|---|---|---|
| 服务流程 `#stepsPanel` | 永远折叠 | `stepsSummary`，**留空 = 自动拼步骤名**（`autoSummary(steps.items.map(title))`） |
| 下单前须知 `#promisePanel` | 永远折叠 | `promisesSummary`，留空 = 自动拼条目名（>4 条只显示前 3 条 + `…`） |
| 常见问题 `#faqPanel` | **每条**一个 `<details>` | 想连整块都折叠：填 `faqPanelSummary`（留空 = 不折叠，就是现在这样） |

⚠️ 两个坑（都写在 `static/style.css` 的注释里）：① 摘要行要横排就把 `display:flex`
写在 **`summary` 自己**身上，别写在 `<details>` 上；② 折叠块的正文外面套一层普通的
`<div class="panel-body">` / `.faq-body`，收起时"一行都不占"交给浏览器原生规则。

## 三之二、★ 客户档案与到期提醒（每天都会用到的那一页）

### 1. 它到底解决什么问题

陪玩按小时、剪辑按项目，这两种都不怕忘。**怕忘的是"包月"的代肝**：
客户 8 月 20 日到期，你要是那天没想起来问一句，他多半也不会主动说 ——
单子就这么悄悄没了（丢一个 50R/月的 = 一年 600R）。

所以这一块的全部价值就一句话：**每天花 1 分钟，就知道今天该催谁。**

### 2. 六张表里的第六张：`customers`（第 802 行起的 `SCHEMA` 里）


### 3. ★ 到期分档（整个功能的灵魂，`customer_level()`，第 2120 行）

```text
days = days_left(end_date)      ← 距离到期还有几天（负数 = 已超期）
   days is None      → none     长期 / 一次性（不算到期，列表里排最后）
   days < 0          → expired  已超期 N 天     ← 红色，最优先
   days == 0         → today    今天到期        ← 红色
   1 <= days <= 3    → soon     3 天内到期      ← 橙色
   4 <= days <= 7    → week     一周内到期      ← 黄色
   days > 7          → ok       正常            ← 灰/绿
   status != active  → paused / ended（暂停、已结束单独两档，不参与上面这套算账）
```

这套名字和颜色写在 `CUSTOMER_LEVELS`（第 2216 行）里。**`/api/admin` 会把它一起发给前端**，
所以前端不用自己写死颜色：它只看 `level` 和 `levelColor`。

两个"必须记住"的点：

- **`daysLeft` 和 `level` 都是后端算好一起返回的**（`customer_view()`，第 2145 行）。
  前端**绝不自己算日期** —— 否则迟早出现"后端说超期、前端说还有 1 天"这种鬼故事；
- **`end_date` 留空 = 长期**，`days_left()` 返回 `None`，这种客户**永远不进待催列表**。
  这是故意的：一次性单子、长期老板，不该天天在催收清单里刷存在感。

### 4. ★ "今天"必须是北京时间的今天（`today_cn()`，第 2045 行）

```python
def today_cn():
    return datetime.now(CN).strftime("%Y-%m-%d")
```

`CN` 就是 `timezone(timedelta(hours=8))`（第 68 行）。**为什么不能直接 `datetime.now()`**：
免费的 Render / PythonAnywhere 跑在 **UTC** 上，比北京时间晚 8 小时 ——
北京时间今天早上 7 点，服务器那边还算"昨天"。用错了会怎样：

- 今天到期的客户会被算成"还有 1 天"，**该催的那天不催**；
- 续费会从昨天开始推，一个月后到期日就整体差一天，越错越多。

`tests\test_customers.py` 第 4 节专门起 `TZ=UTC` / `TZ=America/New_York` / `TZ=Asia/Tokyo`
三个子进程来验这一条（见下面第 6 点的"怎么验证"）。

### 5. ★ 续费的两套算法（`renew_customer()`，第 2319 行）

```
mode="extend"（默认）—— 从**原来的到期日**往后推
    客户还在服务期里：不损失他已经付过的天数
      例：8 月 20 日到期，续 1 个月 → 9 月 20 日（不是 9 月 10 日）

mode="from_today" —— 从**今天**（北京时间）往后推
    适合"停了一阵子、现在重新开始"的客户：今天 + 1 个月
```

**已超期的客户用 extend 会怎样**（这个坑我写进注释和提示里了）：
如果超期很久（比如 3 个月），从原到期日往后推算出来的日期**可能还是过去的** ——
这不算错，只是"补上了那段空窗"。所以后端在这种情况下会额外回一个 `tip`，
让后台弹一句提示，建议他改用「从今天算」。

月份按 **`add_months()`（第 2096 行）** 的规则加：先加月份，日期超出那个月的天数就压到当月最后一天
（1 月 31 日 + 1 个月 = 2 月 28 日，闰年 29 日）。**前端的预览必须用同一套算法**
（`static/admin.js` 里也有一个 `addMonths()`），否则弹窗说 3 月 3 日、存进去却是 2 月 28 日。
★ 收入的"上月 / 近 3 个月"用的是**同一个** `add_months()`（见 `add_months_text()`）——
两处日期算法永远只有一份。

### 6. API 长什么样

| 接口 | 说明 |
|---|---|
| `GET /api/admin` | 多返回 `customers`（已排好序）、`customerStats`、`customerLevels`、`today` |
| `POST /api/admin/customers` | `action` = `create` / `update` / `delete` / `renew`（★ renew 多一个可选的 `amount`，见下一章） |

三个动作**都回同一份最新全量**（`customers` + `customerStats` + `today`），
前端拿到直接整块重画 —— 和 `/api/admin/zones` 一个套路，省得前端自己猜状态。

`GET /api/admin` 里那四个字段的含义：

```
customers      全部客户，**已经按紧急度排好**（超期最久的排最前 → 长期最后）
customerStats  {total, expired, today, soon, week, active, remind}
               注意 soon / week 是**累计**口径：soon = 超期 + 今天 + 3 天内
customerLevels 分档的中文名和颜色（前端照着上色，不写死）
today          北京时间的今天（前端绝不自己算）
```

### 7. 备份与恢复（老备份必须还能导）

- `build_backup()`（第 3219 行）多打包一项 `customers`；
- `apply_backup()`（第 3286 行）里 **`has_customers` 这个判断很关键**：

```text
备份里有 customers  → 整体替换（和 locks / gallery 一样是"覆盖"语义）
备份里没有（老备份）→ 一条都不动（绝不清空主人现有的客户），恢复照常成功
```

坏数据（没名字、日期乱写）也只跳过或置空，**不让整份备份导不进来** ——
备份是最后一道保险，宁可少恢复一条，也不能整份失败。
（★ 收入流水用的是同一套写法：`has_payments`，见下一章第 9 节。）

## 三之五、★ 收入登记 + 月度统计（"第三刀"：钱从哪来、该推什么）

> 这里的编号是按**哪一刀加的**排的，不是阅读顺序：三之三是第一刀（展示墙），
> 三之四是第二刀（待确认），这一节是第三刀（收入）。
> 之所以把它排版在客户那一章之后：它跟"该催谁了"是一对 —— **一个管人，一个管钱**。

客户那一章解决的是"该催谁了"，这一章解决另一个问题：**钱从哪来、该推什么**。

### 1. 它解决什么问题

主人**一个人靠这个吃饭**：陪玩按小时、代肝包月、剪辑 / PS / 建站按项目。
他每天都知道自己收了多少钱（微信里有记录），但他**答不上来**这两个问题：

- **哪个服务最来钱？**（是该多推三角洲，还是该多接剪辑？）
- **哪个客户最舍得？**（谁值得多花点心思维护？）

要回答它们就必须有"一笔一笔的流水"，而记账这件事**最容易半途而废**。
所以这一刀的全部设计都围着一条原则转：

> ★ **登记必须发生在他本来就要做的动作里**，不能让他每天单独记账。

三个入口因此全都挂在已有的动作上：

| 入口 | 什么时候发生 | source | 他多做一步了吗 |
|---|---|---|---|
| ① 确认预约 | 在后台点「已确认」 | `booking` | **没有**（他本来就要点确认） |
| ② 续费 | 续费弹窗里那个金额框（默认已预填） | `renew` | 最多点一下（金额已经帮他填好了） |
| ③ 手动补记 | 收入页右上角「+ 记一笔」 | `manual` | 要动手，但只针对时间表外的单子 |

### 2. `payments` 表：全站**唯一**要求"金额是数字"的地方

```sql
CREATE TABLE IF NOT EXISTS payments (           -- ★ 收入流水
    id          TEXT PRIMARY KEY,               -- uuid4().hex（内部用）
    date        TEXT NOT NULL,                  -- 收款日期 "YYYY-MM-DD"（★ 北京时间的那一天）
    amount      REAL NOT NULL,                  -- ★★ 金额是**数字**
    zone        TEXT DEFAULT '',                -- 哪个分区 / 服务（zones.id）；空 = 没归类
    item        TEXT DEFAULT '',                -- 项目 / 档位名
    customer    TEXT DEFAULT '',                -- 客户称呼（档案删了也还留着他叫什么）
    customer_id TEXT DEFAULT '',                -- 关联客户档案 id（可选）
    source      TEXT DEFAULT 'manual',          -- booking / renew / manual
    ref         TEXT DEFAULT '',                -- 关联单据，★用来防重复记账
    note        TEXT DEFAULT '',
    created_at  INTEGER DEFAULT 0
);
```

> ⚠️ **`amount` 是数字，而 `customers.price` 仍然是自由文本**（第 864 行那一列）。
> 这两个不是"重复了"，是**故意分开的两套东西**：
> 自由文本是主人要的（他写 `20R/月`、`推图15R` 就得原样显示），
> 数字是统计要的（"这个月收了 1240"必须能加总）。**别想着把它们统一起来。**

那数字从哪来？从文本里**抠**出来 —— `parse_amount()`（第 656 行）：

```python
def parse_amount(text):
    m = AMOUNT_NUM_RE.search(str(text if text is not None else ""))
    if not m:
        return None
    try:
        return float(m.group())
    except ValueError:                 # pragma: no cover - 正则已经保证是数字，兜底而已
        return None
```

| 输入 | 结果 | 为什么 |
|---|---|---|
| `"20R/月"` | 20.0 | 最典型的写法 |
| `"推图15R"` | 15.0 | 数字可以夹在中文里 |
| `"100R/月（含月卡5R）"` | **100.0** | **只取第一个数字**（后面那个 5R 是附加说明，加进去就变成 105 了） |
| `"按需报价"` / `""` / `None` | **None** | 抠不出数字 = "算不出钱"，**不能假装是 0** |
| `"0"` | 0.0 | 0 是合法数字 —— 但真正记账那里有 `amount > 0` 的判断，0 元一律不记 |

它在后台的用处只有一个：**续费弹窗的默认值**（`static/admin.js` 的 `payAmountFromText()` 是同一个规矩）。

### 3. ★ 三个记账钩子（以及它们为什么长这样）

```python
def record_booking_payment(lock):
    lock = lock or {}
    if str(lock.get("kind") or "") != "booking":
        return None, "这不是预约单（休息锁不记收入）。"
    try:
        price = float(lock.get("price") or 0)
    except (TypeError, ValueError):
        price = 0
    if price <= 0:
        return None, "这条预约没有金额（price=0），不记流水。"
```

三条规矩（都是为了让流水干净）：

1. **只记 `kind='booking'`** —— 休息锁（`rest`）不是生意，别往收入里塞；
2. **`price` 是 0 就跳过** —— 老板自己锁的时段、免费补偿的单子都不该出现 `¥0` 流水
   （一堆 0 只会让统计表变脏，一点信息量都没有）；
3. **日期 = 这单开始那天**（不是"点确认那天"）—— 他多半是打完之后才点确认的，
   按开始那天算，收入才会落在"这单真正发生"的那个月里（跨月时尤其明显）。
   （`datetime.fromtimestamp(start_ms / 1000, CN)` 就是"这个毫秒时间戳在北京时间是几月几号"。）

另外两个钩子的位置：

| 钩子 | 代码位置 | 记什么 |
|---|---|---|
| ① 确认预约 | `admin_schedule` 的 `confirm-lock` 分支 | `record_booking_payment(confirmed_lock)`，**在 `with _db_lock` 外面调** |
| ② 续费 | `admin_customers` 的 `renew` 分支 | 填了 `amount` 才调 `record_payment(...)`，不填就什么都不做 |
| ③ 手动 | `admin_payments`（`POST /api/admin/payments`） | `clean_payment()` 洗一遍 → `insert_payment()` |

> ⚠️ **前两个钩子都必须在 `with _db_lock` 结束之后调用**。
> `record_payment()` 自己也要拿 `_db_lock`，而它是普通 `Lock`（不可重入）——
> 在锁里再拿一次 = **全站卡死**（就是下面「坑 21」那个）。
> 所以 `confirm-lock` 那一段是这么写的：先在锁里把那条锁**查出来存进变量**
> （`confirmed_lock = dict(row)`），出了 `with` 再记账。

### 4. ★ 幂等：同一单只能有一条流水

```python
def payment_exists(source, ref):
    ref = str(ref or "").strip()
    if not ref:
        return False
    with connect() as conn:
        row = conn.execute("SELECT 1 FROM payments WHERE source=? AND ref=? LIMIT 1",
                           (str(source), ref)).fetchone()
    return row is not None
```

为什么必须有它：老板**会反复点「已确认」**（他可能不记得点过没有），
也可能**恢复一次备份之后又点一遍**。没有这道防线，流水里会出现两笔一模一样的钱，
"这个月收了 1240"就成了假的 —— 而这一页的全部价值就是**他信这个数字**。

`ref` 是什么，两种单据各不一样：

| 来源 | ref | 为什么这么选 |
|---|---|---|
| 确认预约 | **锁的 id** | 一条锁只该有一条 booking 流水 |
| 续费 | **`客户id@新到期日`** | 网络卡了再点一次「确认续费」不该变成两笔钱；而续第二次一定会有新的到期日，所以正常续费永远不会被误判成重复 |
| 手动补记 | **空** | 手记的没有单据号，**ref 为空时不参与幂等检查**（不能因为"两条都是空的"就当成重复） |

### 5. ★ 时间范围与统计口径（一律按北京时间）

```python
def income_range_bounds(pay_range, today=None):
    today = today or today_cn()
    if pay_range not in INCOME_RANGES:
        pay_range = "month"
    first = month_start_text(today)
    next_first = add_months_text(first, 1)
    last = add_days_text(next_first, -1) if next_first else ""
```

| 按钮 | 范围（**闭区间，两端都含**） | 怎么算出来的 |
|---|---|---|
| 本月 | 本月 1 号 ~ 本月最后一天 | 最后一天 = **下月 1 号 - 1 天**（这样闰年 2 月也不会算错） |
| 上月 | 上个月 1 号 ~ 上个月最后一天 | 本月 1 号往前推 1 个月 ~ 本月 1 号 - 1 天 |
| 近 3 个月 | 本月 1 号往前推 2 个月的 1 号 ~ 本月最后一天 | 含本月，一共 3 个自然月 |
| 今年 | 今年 1 月 1 日 ~ 今年 12 月 31 日 | — |
| 全部 | 不设限 | 返回 `("", "")`，空字符串 = 那一端不设限 |

三个口径决定（都在 `income_stats()`（第 2879 行）的注释里写清了）：

1. **"本月"按北京时间判** —— `today_cn()`，和客户到期那一套完全一致。
   服务器在 UTC 时，北京时间 10 月 1 日早上 7 点还是"9 月"，那一个月的账就错了
   （`tests\test_income.py` 第 13 节用 `TZ=UTC / America/New_York / Asia/Tokyo` 验这一条）；
2. **环比 = 上一个自然月**，不是"上一个等长区间"。他想的是"这个月比上个月怎么样"；
3. **上月一笔都没有 → `momPercent` 是 `None`**，界面说「上月没有记录」——
   **绝不显示 0%**（"从无到有"和"没变化"完全是两件事，显示 0% 就是骗人）。

### 6. 页面上的数字从哪来

全部由 `income_stats()`（第 2879 行）一次算好，**前端一个数都不自己算**
（自己算一遍迟早出现"大字说 ¥1240、明细加起来 ¥1230"，那时候他就不信这一页了）：

```
total / count          这个范围的总额和笔数
momPercent / momText   环比（算不出来时 momPercent 是 None）
categories             按大类分的小卡 [{id,name,icon,amount,count}]
                       ★ 分区属于哪个大类由 zones.category 决定；

topServices            哪个服务最来钱（按分区名聚合，前 5）
topCustomers           哪个客户最舍得（按客户称呼聚合，前 5）
records / recordTotal  这个范围的流水明细（最多 100 条）+ 这个范围总共几笔
```

- 每行可以「改」和「删」（删除用原生 `confirm()`，和后台其它危险操作一致）。

### 8. API

| 接口 | 说明 |
|---|---|
| `GET /api/admin` | 多返回 `income`（本月统计）、`payments`（数据库原样的全量流水，给编辑表单用）、`paymentSources`、`incomeRanges` |

### 9. ★ 备份与恢复：`has_payments`（和客户那套一模一样）

```python
    payments, has_payments = [], isinstance(data.get("payments"), list)
```

```text
备份里有 payments  → 整体替换
备份里没有（老备份）→ 一条都不动（绝不清空主人记了几个月的账），恢复照常成功
```

> ⚠️ **为什么收入流水比别的数据更不能丢**：它是"算出来的"，**重建不了** ——

> 少带这一项，换台电脑恢复之后就只剩"这个月 ¥0"，而且永远补不回来。

坏行（金额 0 / 抠不出数字 / 不是字典）跳过；**日期乱写但金额是真的会按今天救回来**
（宁可少一条好日期，也不能丢一笔钱）。恢复摘要里多了 `payments` 一项，后台会显示「收入 N 笔」。

## 三之三、★ 展示墙：外链 + 分类可配置（"第一刀"）

展示墙一开始只服务陪玩（游戏截图 / 老板评价），但**剪辑、PS、建站**的作品也要挂上去：
视频在 B 站、网页在你做的站点上 —— 光传一张封面图，客户看不到成品。所以这一刀加了两件事。

### 1. 外链 `link`（★ 这里有一道**安全**防线）

`gallery` 表多一列 `link`，后台填「点开跳转的链接（选填）」，前台有链接的图就变成
一个**新窗口打开的 `<a>`**（`target="_blank" rel="noopener noreferrer"`），没链接的还是点开放大。

```python
def clean_link(raw):
    text = str(raw or "").strip()
    if not text:
        return ""
    lowered = text.lower()
    if not (lowered.startswith("http://") or lowered.startswith("https://")):
        return ""
    return text[:GALLERY_LINK_MAX]
```

**为什么必须按协议白名单卡死**（`clean_link`，第 713 行）：这个字段最后会变成
`<a href="……">`。要是有人塞 `javascript:alert(1)`，**将来任何一个访客点一下那张图，
就会在页面上执行别人写的代码**（偷 Cookie、假装成网站骗密码、跳钓鱼页）；
`data:text/html;base64,…` 同理。这两种写法浏览器都认，所以"看着像网址"不等于安全 ——
只认 `http://` / `https://`，别的（`javascript:` / `data:` / `vbscript:` / `file:` /
相对路径 / 空的）**一律存成空字符串**，前台就当成"这张图没有外链"。

> 前端 `admin.js` 也会先拦一道（输入框旁边就提示），但那只是"省得白传一张图才被洗掉"，
> **真正管用的是后端这一道** —— 前端永远可以被绕过。测试里第一条断言就是这个。

### 2. 分类可配置 `gallery_categories`（照抄"大类"的写法）

| 存哪 | `store` key=`gallery_categories`，一段 JSON 数组 |
|---|---|
| 长什么样 | `[{"id":"screenshot","name":"游戏截图","sort":1}, …]` |
| 默认三类 | `screenshot 游戏截图` / `review 老板评价` / `work 作品` |
| 函数 | `clean_gallery_categories`（第 1359 行）/ `list_gallery_categories`（第 1388 行）/ `set_gallery_categories`（第 1411 行） |

**和大类（`categories`）唯一的区别：展示墙分类允许删除。** 大类不能删是因为分区会无家可归；
一个展示墙分类删了，图还在，只是要换个归类。

三条规矩（都写在 `admin_gallery_categories`，第 5695 行的注释里）：

1. **`id` 不许改，改名可以** —— 老图的 `category` 字段存的就是 id，改了 id 那些图就对不上号了；
2. **不允许删掉"还有图片在用"的分类** —— 错误里会写清"还剩几张图"，让主人先去把那几张图
   改到别的分类。**为什么不自动把图搬到第一个分类**：那会悄悄改变客户看到的分组
   （比如把"作品"混进"游戏截图"），而主人不会意识到自己刚才那一下动了什么。
   宁可让他先手动挪 —— 5 张图点 5 下，但每一步他都看得见。空分类随便删，一点都不啰嗦。
3. **老数据兜底**：`gallery_categories_for_public()`（第 1286 行）会把"配置里找不到、
   但真的有图在用"的历史分类临时补到列表最后 —— **宁可多一个按钮，也不能让图人间蒸发**。

## 三之四、★ 「待确认」+ 自动释放（"第二刀"）

### 1. 它解决什么问题

客户自助预约**点了就锁定**（主人指定的流程）。但"占住"不等于"这单成立"：
他没加微信、联系不上，那段时间就白占着 —— **时段就是库存，库存就是钱**。
以前后台只有一个数字，没有一个地方能点「确认」或「释放」。

所以客户自助预约默认是 **`confirmed=0`（待确认）**，`locks` 表加两列（都走 `ensure_column`）：

| 列 | 默认 | 含义 |
|---|---|---|
| `confirmed` | **1** | 1=已确认（默认）/ 0=待确认（新的客户自助预约才是 0） |
| `confirmed_at` | 0 | 老板点「已确认」的时间（毫秒；没确认过是 0） |

> ⚠️ **`confirmed` 的默认值必须是 1**。老库里的锁全是老板自己弄的，不该在升级那一刻
> 突然集体变成"待确认" —— 那会让后台一打开就跳出几十条假待办，把真正要处理的淹掉。
> 只有**新提交的**客户自助预约才会显式写成 `confirmed=0`（见 `create_booking`，第 3714 行）。

### 2. 三个核心函数

```python
def pending_locks(now_ms=None):
    now_ms = now_ms or int(time.time() * 1000)
    out = [dict(lk) for lk in list_locks()
           if lk.get("source") == "client" and not lock_confirmed(lk) and int(lk["end"]) > now_ms]
    out.sort(key=lambda lk: (int(lk.get("created_at") or 0), int(lk["start"])))
    return out
```

- `pending_locks()`（第 3822 行）—— **待办清单的唯一来源**。三个条件缺一不可：
  `source='client'`（只有客户自助预约才要确认）、`confirmed=0`、`end > now`（结束了就不提醒）。
  **等得最久的排最前**，因为等得越久越可能已经黄了；
- `pending_locks_view()`（第 4006 行）—— 在上面那份基础上拼一句中文 `summary`
  （`小明 · 微信 wx_xiaoming · 三角洲行动 · 机密·零号大坝 · 10月15日 20:00–22:00 · 2小时 ¥30`），
  后台照着它直接显示；"已经等了 N 小时"由前端用 `created_at` 和**服务器时间**算；
- `auto_release_expired()`（第 3940 行）—— 见下。

### 3. ★ 自动释放为什么是"惰性清理"，以及它的四道安全阀

这个站跑在免费托管上（PythonAnywhere / Render），**没有常驻的定时器**可言，
加 cron 又是多一件要维护的事。所以是在 `/api/public` 和 `/api/admin` 每次请求时顺手看一眼 ——
老板一定会来后台看，客户一定会来刷时间表，**检查的时机正好是需要它生效的时机**。

```python
    hours = get_auto_release_hours()
    if hours <= 0:
        return 0
    now_ms = now_ms or int(time.time() * 1000)
```

四道安全阀（**任何一个不满足都不删**，这是"删数据"的功能，必须保守）：

1. **设置是 0 → 直接返回**（默认就是 0，等于这个功能根本不存在）；
2. 只删 `source='client'` 且 `confirmed=0` 的 —— 你点过「已确认」的、你自己锁的一律不碰；
3. **只删 `start > now` 的**（还没开始的时间）；已经开始或已经过去的不动 ——
   客户昨天真的打过了，那单不能因为"你没点确认"就被抹掉；
4. `created_at` 是 0 的老数据**不参与**（算不出等了多久，宁可不删）。

**为什么默认 0（关闭）**：悄悄删掉客户占的时间这种事，不能替主人做主 ——
客户可能是半夜下的单，早上才看到。必须由他自己在后台打开。

**删了要留痕**：释放过哪几单记在 `store` key=`auto_released_log`（只留最近 10 条），
后台待确认区下面直接显示「最近自动释放：2 单（小明 10月15日 20:00）」。
为什么落库而不是只放在接口响应里：老板不一定在"刚发生"的那一秒打开后台，他可能第二天才来看。

> **节流**：`AUTO_RELEASE_CHECK_SECONDS`（默认 30 秒）—— 同一个人狂刷页面不会反复查库。
> 设置一变就立刻清掉节流（`_auto_release_last_hours`），所以刚点完「保存」马上生效。
> 自检脚本把它设成 0，这样测试能在几秒内连着验 5 种边界。

### 4. 两个新动作（`POST /api/admin/schedule`）

| action | 请求 | 干了什么 |
|---|---|---|
| `confirm-lock` | `{action, id}` | `confirmed=1` + `confirmed_at=now`；锁还在；★ **顺手记一笔收入**（`source='booking'`，幂等） |
| `release-lock` | `{action, id}` | 删掉这条锁，时间回到可约；**只允许释放待确认的**（传错 id 也删不掉一条已确认的预约） |
| `set-auto-release` | `{action, hours}` | 保存"待确认超过几小时自动释放"（0 = 关闭） |

> **为什么不复用 `remove-lock` 而要单独一个 `release-lock`**：两者做的事确实一样（都是 DELETE），
> 但语义完全不同 —— `remove-lock` 是"取消一个已经成立的预约"，`release-lock` 是
> "这单我还没接，把时间还给别人"。分开的好处：前端语义清楚、后端能单独做校验
> （只允许释放待确认的）、将来想在"释放"时顺手做别的不用再分叉。

> ⚠️ **`set-auto-release` 必须在 `_db_lock` 外面处理**。`set_auto_release_hours()` 里会走
> `set_store()`，而 `set_store()` 自己也要拿 `_db_lock`；`_db_lock` 是普通的 `Lock`
> （不是可重入的 `RLock`），**在锁里面再拿一次 = 直接死锁，整个网站卡住不响应**。
> 这个坑我真踩过一次（写完就自检：服务端不再响应任何请求，日志停在那一行），
> 所以代码里那一段上面写了显眼的注释。**给 `_db_lock` 里加调用之前，先确认它不会回头写库。**

### 5. 后台的两块 UI

- **待确认区块**（`#pendingPanel`，在「预约与时间」页最上面、时间表之上）：
  橙红边框，每行一句话 + 「已确认」/「释放时段」两个按钮，一条都没有时显示
  `没有待确认的预约 ✓`；
- **今日待办条**（`#todoBar`，在标签栏**上方**那条通栏）：
  `📌 今天：3 单要打 · 2 个客户要催 · 1 单待确认`，三个数字**全部来自已有的 `/api/admin` 返回**
  （没有新接口），每一项可点（跳到对应标签页），全为 0 时显示
  `今天没有待办，安心打单～`。

三个数字的口径写在 `static/admin.js` 的 `renderTodoBar()` 上面：

```
📌 今天要打 = 今天（北京时间）里所有 kind='booking' 的锁数（和 renderStats 同一个 todayLocks()）
📞 客户要催 = customerStats.remind（后端算的"已超期 + 7 天内到期"，和「客户」页完全一致）
✅ 待确认   = pendingLocks 的条数
```

> ★ **待办条上没有"收入"这一项，这是故意的**（第三刀特意确认过）：
> 那是"今天要干什么"，不是"这个月赚了多少"。
> 钱的事在「收入」标签页，两件事不要混在一行里 —— 混了以后他扫一眼分不清
> "3 单要打"和"¥1240"哪个是待办、哪个是结果。

## 三之六、★ 文案可改 + 服务条款 + 图片显示位置（"第四刀"）

> 编号还是按"哪一刀加的"排：三之三是第一刀（展示墙）、三之四是第二刀（待确认）、
> 三之五是第三刀（收入），这一节是第四刀。
>
> **这一刀要解决的是主人自己提出来的窟窿**：他说得很直接 ——
> "每一个客户能看到的中文文案，都必须能在后台改。" 以前这些话写死在
> `templates/*.html` 和 `static/*.js` 里，想改一句「看看我能做什么」得先学会改代码。

### 1. 一份目录，三处使用（★ 这一刀最重要的一行代码）

所有文案的**目录**只有一份：`app.py` 的 `TEXT_GROUPS`（第 208 行起）。它是分组 + 每条的
`key` / 说明 / 默认值 / 长度上限，一共 90 多条。三处都用它：

```
TEXT_GROUPS（app.py，唯一的一份目录）
   ├── 后台「文案」标签页：/api/admin 的 textGroups → admin.js 自动画出输入框
   ├── 前台取值：site_summary() 的 texts → site.js / zone.js 的 tx('heroIntro', …)
   └── 备份：build_backup() 的 texts（只带改过的那几句）
```

**为什么这么做**：如果后台那 90 多个输入框在 `admin.html` 里手写一遍，
以后加一句话就要改"目录 + HTML + JS"三个地方，迟早对不上（这个项目已经因为
"两处要同步"踩过好几次坑了）。现在加一句文案 = **在目录里加一行**。

### 2. 只存"和默认不一样"的那几句（`clean_texts()`，第 760 行）

```python
def clean_texts(raw):
    raw = raw if isinstance(raw, dict) else {}
    out = {}
    for key, default in DEFAULT_TEXTS.items():
        if key not in raw:
            continue
        text = str(raw.get(key) or "").strip()[:TEXT_LIMITS[key]]
        if not text or text == default:
            continue
        out[key] = text
    return out
```

三条规矩，都在这个函数里：

| 情况 | 结果 | 为什么 |
|---|---|---|
| 传了空字符串 | **不存** = 用默认 | 这就是后台那句"留空 = 用默认那句话" |
| 填得和默认一字不差 | **不存** | 后台的输入框里预填的就是"现在生效的那句"，原样存下来会把所有默认值钉死；以后默认值改好了他就收不到了 |
| 不认识的 key | 丢掉 | 白名单，防止有人往 store 里塞奇怪的东西 |

所以 `get_texts()`（第 4285 行）= **默认值打底 + 覆盖值盖上去**，前台永远拿得到每一句，
JS 那边不用自己写兜底；`save_texts()` / `reset_texts()` 只管这份覆盖表。

> ⚠️ **保存是"整页覆盖"语义**：后台每次点「保存文案」发的是全部 90 多格，
> 所以"清空某一格 = 那一句回默认"才成立。写测试的时候要注意这一点
> （`tests\test_texts.py` 里那个 `OVERRIDES` 就是为此存在的）。

### 3. 文案里的花括号是"变量"

| 占位符 | 变成什么 | 谁替换 |
|---|---|---|
| `{name}` | 你的昵称 | 前台 `tx()`（`static/site.js` / `static/zone.js`） |
| `{zone}` | 游戏名 / 分区名 | 前台 `tx()` |
| `{max}` | 一次最多几小时 | 前台 `tx()`（值来自 `zone.js` 的 `MAX_HOURS`） |
| `{wechat}` | 你的微信号 | **后端**（`terms_fill_vars()`，条款页是服务端渲染的） |

为什么要留这些占位符：那句话里带着你的昵称和上限数字。写死的话，
你改个昵称、或者把"一次最多 6 小时"改成别的，文案就和实际规则对不上了。
（改文案时**别把占位符删掉**，删了它就原样显示成 `{name}`。）

### 4. 文案是纯文本，不认 HTML（这是安全底线）

前台一律 `textContent` / `escapeHtml()`，后端拼条款 HTML 时也全部 `escape_html()`。
所以主人在文案里写 `<b>加粗</b>`，客户看到的就是这串字符本身。

**为什么不支持 HTML**：文案存在数据库里、由后台输入框编辑 —— 一旦允许标签，
它就变成"任何拿到后台的人都能往客户页面上塞 `<script>`"的入口
（而主人是要把后台网址存进手机书签的）。代价是几条 `<b>` 没了，值得。

### 5. 服务条款（`terms_view()`，第 4387 行）

```
store key='terms' → {"title": "服务条款", "updated": "2026-10-14",
                     "sections": [{"heading": "一、我能提供什么", "body": "…"}, …]}
```

- 默认内容在 `DEFAULT_TERMS`（第 385 行起）：7 节，照"个人接单"的实际情况写的
  （服务内容 / 下单与确认 / 付款 / 取消与改期 / **账号安全** / 责任范围 / 联系方式）；
- `updated` 是**服务器在保存时自动写上的**（北京时间今天），不让前端传 ——
  手填的日期百分之百会忘记改；
- `terms_sections_html()`（第 4443 行）负责把正文变成 HTML：**空行 = 一个 `<p>`，
  单个换行 = `<br>`**，所以条款里那种"· 一条一条"的写法不会挤成一坨；
- `/terms` 页面由 `serve_terms()`（第 4810 行）**服务端渲染**，故意不用 JavaScript：
  客户不装 JS 也能看全，微信抓分享卡片、搜索引擎爬到的也是完整内容。

### 6. 图片显示位置（`clean_image_position()`，第 740 行）

哪些图会被裁、哪些不会 —— 是**逐个去看 CSS 确认**的，不是猜的：

| 图片 | CSS | 会裁吗 | 给九宫格了吗 |
|---|---|---|---|
| 首页整页背景图 | `.site-bg`：`background-size: cover` | 会 | ✅ |
| 分区页背景图 | `.zone-hero-bg`：`background-size: cover` | 会 | ✅ |
| 首页 / 分区首屏主视觉 | `.hero-media img`：`object-fit: cover` + `max-height: 430px` | 会 | ✅ |
| 头像 | `.avatar`：`object-fit: cover` | 会 | ✅ |
| 微信二维码 | `.wechat-card img`：`object-fit: contain` | 不会（整张缩进画面） | ❌ |
| 价目表长图 | `.price-sheet img`：宽度 100%、高度自动 | 不会 | ❌ |
| 微信分享图 | 由微信 / QQ 自己裁卡片 | 控制不了 | ❌ |
| 展示墙的图 | `.gallery-item img`：`object-fit: cover`、高 170px | 会 | ❌（一批图共用一套样式，单张控制要加一列字段 + 一堆界面，先不做） |

**存在哪**：跟着图片走 —— 首页那三张在**全局资料**里（`avatarPosition` /
`backgroundPosition` / `heroImagePosition`），分区那两张在**分区资料**里
（`backgroundPosition` / `heroImagePosition`）。这样"保存主页设置 / 保存这个分区"
就顺手把它一起存了，备份也不用改（profile 整个都在备份里）。

**脏值怎么办**：读的时候统一过 `clean_image_position()` —— 不是 9 个合法值之一
就退回 `center`。所以**库里存了脏值最坏也只是回到原来的观感**，绝不会把奇怪的字符串
塞进 CSS 里。

> 一个小机关：`clean_zone_profile()` 里那两个位置字段是在白名单循环**之外**单独处理的 ——
> `ZONE_TEXT_KEYS` 只做"截断"，而位置需要"按 9 个值校验"，混在一起会写错。

### 3. 老数据库怎么补字段（第 921 行 `ensure_column`）

这是加功能时最关键的一小段。`CREATE TABLE IF NOT EXISTS` **只负责建新表**，
表已经存在时它一行都不改——所以你线上那个跑了一阵的数据库，直接查新字段会报 `no such column`。

```python
def ensure_column(cur, table, column, decl):
    cols = [row[1] for row in cur.execute("PRAGMA table_info(%s)" % table).fetchall()]
    if column in cols:
        return False
    cur.execute("ALTER TABLE %s ADD COLUMN %s %s" % (table, column, decl))
    return True
```

**先问"这个字段在不在"，缺了才加。** 所以 `init_db()` 跑一百遍也不会出错，
而且 `ALTER TABLE ADD COLUMN` 只是加一列，**你原来的预约记录一条都不会丢**。

### 4. 为什么时间表不用存（第 3618 行 `slot_status`）

这是全站最值得看懂的 20 行（为了讲解，我在几行后面加了 `# 1.` `# 2.` 这样的序号注释，
代码本身是原样的）：

```python
def slot_status(start_ms, end_ms, now_ms, locks, rules, accepting):
    if end_ms <= now_ms:
        return "past"                     # 1. 已经过去了
    for lk in locks:                      # 2. 被手动锁定？
        if lk["start"] < end_ms and start_ms < lk["end"]:
            return "booking" if lk["kind"] == "booking" else "rest"
    for rule in rules:                    # 3. 命中固定休息规则？
        if rule["enabled"] and rule_covers(rule, start_ms):
            return "rest"
    if not accepting:
        return "closed"                   # 4. 你关掉了接单总开关
    return "free"                          # 5. 都没有 → 可预约
```

**判断顺序就是业务规则。** 想让"停接"优先于"休息"？把第 4 步挪到第 3 步前面就行。

### 5. 客户点「立即锁定时间」之后发生了什么（第 3714 行 `create_booking`）

前台不再是"生成一段文案让你手动锁"，而是**点了就锁**：

```python
    with _db_lock, connect() as conn:
        now_ms = int(time.time() * 1000)
        status_of = {s["start"]: s["status"] for s in build_slots(now_ms)}
```

1. **拿到写锁**（`_db_lock`）之后才复查空档 —— 两个人同时点同一格，只会有一个成功；
2. 只要有**任何一格**不是 `free`，就整体拒绝，返回 409 并告诉客户是哪几个小时（不会锁一半）；
3. 全部空闲 → 用 `merge_hour_runs()` 把**连续的小时合并成段**，每段插一条
   `source='client'` 的锁，**顺手记下 `zone`（这单来自哪个分区）**；
4. 价格 = 该段小时数 × 模式单价（模式来自**这个分区自己的 `prices`**）；
5. 最后 `notify_owner()` 给你推一条通知（正文第一行写着是哪个分区的单）。

### 6. 为什么通知要丢到后台线程（第 4608 行 `notify_owner`）

```python
    threading.Thread(target=worker, daemon=True).start()
    return True
```

给微信/PushPlus 发请求要几百毫秒甚至超时 10 秒。**如果同步发，客户就要陪着等**，
网络不好还会看到"提交失败"——可实际上时间已经锁好了。
所以这里是"**先回答客户，再慢慢发通知**"，发送结果写进 `store` 表的 `notify_last`，后台直接能看到成功还是失败。

### 7. 跨午夜规则怎么算（第 3594 行 `rule_covers`）

固定休息支持 `22:00 → 06:00` 这种跨过零点的写法，很容易写错：

```python
    span_hours = 24 - start_hour if end_hour == 24 else (end_hour - start_hour) % 24
```

- `02:00 → 10:00`：`(10-2) % 24 = 8` 小时 ✓
- `22:00 → 06:00`：`(6-22) % 24 = 8` 小时 ✓（负数取模会自动绕回来，这是 Python 的特性）
- `00:00 → 24:00`：整天，要单独处理，所以前面加了个 `if end_hour == 24`

下面那个 `for back in (0, 1)` 是干什么的：跨午夜的规则可能是**昨天**开始的，
所以要把"今天"和"昨天"两条基准线都试一遍。

### 8. 168 个格子是怎么来的（第 3650 行 `build_slots`）

```python
def build_slots(now_ms=None):
    """生成未来 7 天 × 24 小时 = 168 个格子。"""
    now_ms = now_ms or int(time.time() * 1000)
    start0 = midnight_ms(now_ms)
```

就两句话：**从今天 0 点开始，每格 1 小时，连着排 168 格**。
没有数据库查询、没有缓存，每次请求都重新算——所以它永远是最新的。
**注意它连分区参数都没有**：不管哪个分区来问，答案都一样。

### 9. 密码为什么不是明文（第 1098 行 `hash_password`）

```python
def hash_password(password):
    salt = secrets.token_hex(8)
    digest = hashlib.pbkdf2_hmac("sha256", password.encode("utf-8"), salt.encode("utf-8"), 120_000)
    return salt + "$" + digest.hex()
```

`pbkdf2_hmac` 把密码"单向搅拌"12 万次。数据库里存的是搅拌结果，**没法反推回原密码**。
`salt`（盐）是随机串，作用是：就算两个人用同样的密码，存进去的结果也不一样。

验证时不是"比对字符串"，而是**用同样的盐再搅拌一次**看结果是否相同（第 1104 行 `verify_password`）。

### 10. 登录为什么重启后还在（第 4486 行 `new_session`）

```python
def new_session():
    expires = int(time.time()) + SESSION_HOURS * 3600
    sig = hmac.new(session_key(), str(expires).encode(), hashlib.sha256).hexdigest()[:32]
    return "%d.%s" % (expires, sig)          # Cookie 长得像 1791785399.3533f78e…
```

**服务器不存任何会话**：Cookie 自己带着"过期时间 + 签名"。
签名密钥 = 你的密码哈希（`session_key()`），所以你一改密码，所有旧 Cookie 立刻失效。
`secrets.compare_digest` 是"防时序攻击"的比对方式——安全领域的标准写法。

### 11. 所有请求的总入口（第 4993 行起）

```python
def do_GET(self):

    if path in ("/", "/index.html"):

        return self.send_file(...)
```

**这就是一张路由表**：左边是网址，右边是处理函数。

### 12. 为什么并发不会出错（第 911 行）

```python

```

```python

        conn.execute("UPDATE ...")
```

网站是多线程的（你和客户可能同时点）。**所有写操作排成一队**，一次只让一个人写，

### 13. 图片是怎么存的（第 3176 行 `save_data_url`）

```python
def save_data_url(data_url):
    m = re.match(r"^data:image/(png|jpeg|jpg|webp);base64,(.+)$", str(data_url), re.S)
    blob = base64.b64decode(m.group(2))
    key = uuid.uuid4().hex + "." + ext          # 随机文件名，避免重名
    with open(os.path.join(UPLOAD_DIR, key), "wb") as f:
        f.write(blob)
    return "/api/media/" + key, None            # 数据库里只存这个网址
```

前端把图片转成 `data:image/webp;base64,...` 这种文本传过来，后端解码存成文件，
**数据库里只记一个网址**。这就是为什么备份要单独把图片打包进去
（第 3213 行 `build_backup`，分成 `profileImages` 全局的 和 `zoneImages` 每个分区的）。

### 14. 从首屏图自动提取主色（第 1850 行 `extract_dominant_color`）

后台「从首屏图自动提取主色」按钮后面就是这 25 行：

1. 用 PIL 打开图片、缩到 80×80；
2. `quantize(colors=8)` 把颜色压成 8 种，数一数哪个出现最多；
3. 把选中的颜色**往亮里推一推**（`_brighten()`）——
   主人的图多半是深色游戏截图，直接取出来偏灰偏暗，当主色会看不清。

> ⚠️ PIL 是**唯一**的第三方依赖，而且只是"锦上添花"：`import PIL` 失败、
> 图片坏掉、格式不认识 —— 一律返回"取不了色"的中文提示，**绝不让网站起不来**。

## 七、下一步该看什么

1. 打开 `app.py`，用 Ctrl+F 搜 `def slot_status`，把那段读三遍——你就懂了 80%。
2. 打开浏览器 F12 → Network，刷新 `/z/delta`，点开 `api/public?zone=delta` 看返回的 JSON——和代码对上号。
3. 在后台「分区管理」建一个新分区、传一张图、填两行价格，然后打开 `/z/新id` 看效果。
4. 想再接一种通知方式（比如邮件），照着 `send_notify()` 里的 `pushplus` 那一支抄一份即可。
5. 想改催续费的话术？`static/admin.js` 的 `renewMessage()` —— 那是唯一一处模板，改完刷新页面就生效。
6. 想改收入页那句话（"上月没有记录"之类）？`app.py` 的 `income_stats()`（第 2879 行）里
   那几行 `mom_text = ...` —— 数字口径和文案在同一处，改的时候不会只改到一半。
7. 想知道"哪些服务最赚钱"，除了后台那一页，也可以直接看 `data/site.db` 的 `payments` 表：
   `SELECT zone, SUM(amount) FROM payments GROUP BY zone;`（**只读**，别改。改之前先导备份。）
8. 想给客户看的某句话换个说法？先翻 `app.py` 的 `TEXT_GROUPS`（第 203 行起）——
   大概率它已经在目录里了，那就不用改代码，后台「文案」里直接改。
