# 代码导读：这个网站到底是怎么跑起来的

这份文档的目标只有一个：**让你打开 `app.py` 不再发懵**。

读法建议：不用从头读到尾。先看下面的"全景图"，然后挑你最想改的那一节看。
行号是我写这份文档时从真实文件里提取的，**你改过代码之后行号会变，以函数名为准**。

---

## 一、全景图：客户打开一次网页，发生了什么

```
客户手机（微信里点开链接）
   │
   │ 1. 请求 https://你的域名/
   ▼
┌──────────────────────────────────────────────────┐
│  app.py（在 Render / PythonAnywhere 上跑着）      │
│                                                  │
│  do_GET()  ← 所有读请求都从这里进（第 1010 行）    │
│     ├─ "/"          → serve_index() 现拼 HTML     │
│     ├─ "/static/…"  → 直接发文件                  │
│     └─ "/api/public"→ build_slots() 现算 168 格   │
│                          ↑                       │
│                     slot_status() 判断每一格      │
│                                                  │
│  do_POST() ← 客户点「立即锁定时间」走这里          │
│     └─ "/api/book"  → create_booking() 立刻锁定   │
│                          └→ notify_owner() 推给你 │
└──────────────┬───────────────────────────────────┘
               │ 2. 读/写
               ▼
        data/site.db（SQLite 文件）
        ├─ store    你的资料、密码、上次导出时间、通知配置
        ├─ locks    被锁定的时段（预约 / 休息）
        ├─ rules    固定休息规则
        └─ gallery  展示墙
               │
               │ 3. 返回 JSON
               ▼
客户浏览器里的 site.js → 把 JSON 画成时间表
```

**一句话总结**：服务器**不保存页面**，每次请求都现场算一遍再发出去。
所以你改一条休息规则，整周时间表立刻跟着变。

## 三、必须看懂的片段

### 1. 配置区：改行为先看这里（第 39–107 行）

```python
DAYS_SHOWN = 7                 # 时间表显示未来几天
MAX_SELECT_HOURS = 72          # 一次最多能勾选多少小时
MAX_BOOK_HOURS = 6             # 客户自助预约一次最多能锁多少小时
SESSION_HOURS = 12             # 登录有效期（小时）
DEFAULT_PASSWORD = os.environ.get("ADMIN_PASSWORD") or "baixu123"
PORT = int(os.environ.get("PORT") or 8123)
```

`os.environ.get(...)` 的意思是"先看环境变量，没有就用后面的默认值"。
**Render / PythonAnywhere 就是靠环境变量把 `PORT` 和 `ADMIN_PASSWORD` 传进来的**——这就是为什么同一份代码在你电脑上是 8123、在服务器上是别的端口。

> `MAX_SELECT_HOURS`（72）是**后台**批量锁定的上限；客户在前台自助预约走的是 `MAX_BOOK_HOURS`（6），
> 故意卡得更紧，免得有人一口气把你一周的空档全占了。前端 `site.js` 里也有一个 `MAX_HOURS`，改的时候要一起改。

### 2. 四张表（第 110–505 行）

```sql
CREATE TABLE IF NOT EXISTS locks (      -- 被锁定的时段
    id TEXT PRIMARY KEY,
    kind TEXT NOT NULL,                 -- booking=预约 / rest=休息
    start INTEGER NOT NULL,             -- 毫秒时间戳
    end INTEGER NOT NULL,
    client TEXT,                        -- 老板称呼（仅自己可见）
    note TEXT,
    source TEXT,                        -- owner=自己锁的 / client=客户自助预约
    mode TEXT,                          -- 模式名（客户选的那一档报价）
    price INTEGER,                      -- 这一段的总价（元）
    contact TEXT,                       -- 客户联系方式
    contact_type TEXT,                  -- wechat 微信 / xianyu 闲鱼 / qq QQ
    created_at INTEGER);                -- 下单时间（毫秒时间戳）
```

**注意时间存的是"毫秒数"不是"2026-10-12 20:00"这种文字。**
为什么？因为时间戳没有时区歧义、能直接比大小。你在后台看到的"10月13日 20:00"是前端换算出来的。

### 3. 老数据库怎么补字段（第 170 行 `ensure_column`）

这是这次加功能时最关键的一小段。`CREATE TABLE IF NOT EXISTS` **只负责建新表**，
表已经存在时它一行都不改——所以你线上那个跑了一阵的数据库，直接查新字段会报 `no such column`。

```python
def ensure_column(cur, table, column, decl):
    cols = [row[1] for row in cur.execute("PRAGMA table_info(%s)" % table).fetchall()]
    if column in cols:
        return False
    cur.execute("ALTER TABLE %s ADD COLUMN %s %s" % (table, column, decl))
    return True
```

**先问"这个字段在不在"，缺了才加。** 所以 `init_db()` 跑一百遍也不会出错，
而且 `ALTER TABLE ADD COLUMN` 只是加一列，**你原来的预约记录一条都不会丢**
（老记录的 `source` 会自动变成 `owner`，也就是"老板自己锁的"）。

### 4. 为什么时间表不用存（第 552–597 行）

这是全站最值得看懂的 20 行（为了讲解，我在几行后面加了 `# 1.` `# 2.` 这样的序号注释，
代码本身是原样的）：

```python
def slot_status(start_ms, end_ms, now_ms, locks, rules, accepting):
    if end_ms <= now_ms:
        return "past"                     # 1. 已经过去了
    for lk in locks:                      # 2. 被手动锁定？
        if lk["start"] < end_ms and start_ms < lk["end"]:
            return "booking" if lk["kind"] == "booking" else "rest"
    for rule in rules:                    # 3. 命中固定休息规则？
        if rule["enabled"] and rule_covers(rule, start_ms):
            return "rest"
    if not accepting:
        return "closed"                   # 4. 你关掉了接单总开关
    return "free"                          # 5. 都没有 → 可预约
```

**判断顺序就是业务规则。** 想让"停接"优先于"休息"？把第 4 步挪到第 3 步前面就行。
（这就是练习手册里练习 10 让你做的事。）

### 5. 客户点「立即锁定时间」之后发生了什么（第 624 行 `create_booking`）

前台不再是"生成一段文案让你手动锁"，而是**点了就锁**。整个流程在 `create_booking()` 里：

```python
    with _db_lock, connect() as conn:
        now_ms = int(time.time() * 1000)
        status_of = {s["start"]: s["status"] for s in build_slots(now_ms)}
```

1. **拿到写锁**（`_db_lock`）之后才复查空档 —— 两个人同时点同一格，只会有一个成功；
2. 只要有**任何一格**不是 `free`，就整体拒绝，返回 409 并告诉客户是哪几个小时（不会锁一半）；
3. 全部空闲 → 用 `merge_hour_runs()` 把**连续的小时合并成段**，每段插一条 `source='client'` 的锁；
4. 价格 = 该段小时数 × 模式单价，`created_at` 记下**下单时间**；
5. 最后 `notify_owner()` 给你推一条通知。

### 6. 为什么通知要丢到后台线程（第 844 行 `notify_owner`）

```python
    threading.Thread(target=worker, daemon=True).start()
    return True
```

给微信/PushPlus 发请求要几百毫秒甚至超时 10 秒。**如果同步发，客户就要陪着等**，
网络不好还会看到"提交失败"——可实际上时间已经锁好了。
所以这里是"**先回答客户，再慢慢发通知**"，发送结果写进 `store` 表的 `notify_last`，后台直接能看到成功还是失败。

### 7. 跨午夜规则怎么算（第 528–549 行）

固定休息支持 `22:00 → 06:00` 这种跨过零点的写法，很容易写错：

```python
    span_hours = 24 - start_hour if end_hour == 24 else (end_hour - start_hour) % 24
```

- `02:00 → 10:00`：`(10-2) % 24 = 8` 小时 ✓
- `22:00 → 06:00`：`(6-22) % 24 = 8` 小时 ✓（负数取模会自动绕回来，这是 Python 的特性）
- `00:00 → 24:00`：整天，要单独处理，所以前面加了个 `if end_hour == 24`

下面那个 `for back in (0, 1)` 是干什么的：跨午夜的规则可能是**昨天**开始的，
所以要把"今天"和"昨天"两条基准线都试一遍。

### 8. 168 个格子是怎么来的（第 584–597 行）

```python
def build_slots(now_ms=None):
    """生成未来 7 天 × 24 小时 = 168 个格子。"""
    now_ms = now_ms or int(time.time() * 1000)
    start0 = midnight_ms(now_ms)
```

就两句话：**从今天 0 点开始，每格 1 小时，连着排 168 格**。
没有数据库查询、没有缓存，每次请求都重新算——所以它永远是最新的。

### 9. 密码为什么不是明文（第 260–280 行）

```python
def hash_password(password):
    salt = secrets.token_hex(8)
    digest = hashlib.pbkdf2_hmac("sha256", password.encode("utf-8"), salt.encode("utf-8"), 120_000)
    return salt + "$" + digest.hex()
```

`pbkdf2_hmac` 把密码"单向搅拌"12 万次。数据库里存的是搅拌结果，**没法反推回原密码**。
`salt`（盐）是随机串，作用是：就算两个人用同样的密码，存进去的结果也不一样。

验证时不是"比对字符串"，而是**用同样的盐再搅拌一次**看结果是否相同（第 266 行 `verify_password`）。

### 10. 登录为什么重启后还在（第 722–739 行）

```python
def new_session():
    expires = int(time.time()) + SESSION_HOURS * 3600
    sig = hmac.new(session_key(), str(expires).encode(), hashlib.sha256).hexdigest()[:32]
    return "%d.%s" % (expires, sig)          # Cookie 长得像 1791785399.3533f78e…

def session_valid(token):
    payload, _, sig = token.partition(".")
    expect = hmac.new(session_key(), payload.encode(), hashlib.sha256).hexdigest()[:32]
    if not secrets.compare_digest(sig, expect):   # 签名对不上 → 假造的
        return False
    return int(payload) > time.time()              # 还要没过期
```

**服务器不存任何会话**：Cookie 自己带着"过期时间 + 签名"。
签名密钥 = 你的密码哈希（`session_key()`），所以你一改密码，所有旧 Cookie 立刻失效。
`secrets.compare_digest` 是"防时序攻击"的比对方式——安全领域的标准写法。

### 11. 所有请求的总入口（第 1010 行起）

```python
def do_GET(self):
    path, query = unquote(parsed.path), parse_qs(parsed.query)
    if path in ("/", "/index.html"):
        return self.serve_index()
    if path in ("/admin", "/admin/"):
        return self.send_file(...)
    if path.startswith("/static/"):
        ...                          # 静态文件（含 img 子目录）
    if path == "/api/ping":
        return self.send_json({"ok": True, ...})
    if path == "/api/public":
        return self.send_json({...})
    ...
```

**这就是一张路由表**：左边是网址，右边是处理函数。
想加一个新接口，就在这里加一个 `if`；写接口（要登录的）加在 `do_POST`（第 1124 行）里。
客户自助预约 `/api/book` 就加在 `do_POST` 的最前面——它是**唯一一个不需要登录**的写接口。

### 12. 为什么并发不会出错（第 154 行）

```python
_db_lock = threading.Lock()      # 全局写锁
```

```python
    with _db_lock, connect() as conn:      # 所有"写数据库"的地方都这么写
        conn.execute("UPDATE ...")
```

网站是多线程的（你和客户可能同时点）。**所有写操作排成一队**，一次只让一个人写，
就不会出现"两个人同时改一条记录，改丢一个"。读操作不用排队（WAL 模式允许同时读）。

### 13. 图片是怎么存的（第 340–360 行）

```python
def save_data_url(data_url):
    m = re.match(r"^data:image/(png|jpeg|jpg|webp);base64,(.+)$", str(data_url), re.S)
    blob = base64.b64decode(m.group(2))
    key = uuid.uuid4().hex + "." + ext          # 随机文件名，避免重名
    with open(os.path.join(UPLOAD_DIR, key), "wb") as f:
        f.write(blob)
    return "/api/media/" + key, None            # 数据库里只存这个网址
```

前端把图片转成 `data:image/webp;base64,...` 这种文本传过来，后端解码存成文件，
**数据库里只记一个网址**。这就是为什么备份要单独把图片打包进去。

## 四、实战：想加一个功能，该改哪几处

假设你想加一个"**关于我**里多一行『常用语音软件：YY 123456』"：

| 步骤 | 改哪里 | 怎么改 |
|---|---|---|
| 1. 数据 | `app.py` 的 `DEFAULT_PROFILE`（第 75 行） | 加一行 `"voice": "",` |
| 2. 后台表单 | `templates/admin.html` 的资料面板 | 复制一个 `<div class="field">` 区块，改 id |
| 3. 后台读取 | `static/admin.js` 的 `fillProfileForm()` 和 `collectProfile()` | 各加一行（填进去 / 收回来） |
| 4. 前台显示 | `templates/index.html` 的「关于我」区块 | 加一个空标签，比如 `<p id="aboutVoice"></p>` |
| 5. 前台渲染 | `static/site.js` 的 `renderProfile()` | 加一行 `$('#aboutVoice').textContent = p.voice;` |
| 6. 验证 | 命令行 | `python tests\run_tests.py`（接口 120 项 + 预约 75 项，会告诉你有没有改坏） |

**规律：一个字段要穿过"数据库 → 后台表单 → 后台脚本 → 前台页面 → 前台脚本"五层。**
加过一次之后，你再看任何网站都会觉得眼熟。

> 不需要重启就能看到效果的是 `.html` / `.js` / `.css`（Ctrl+F5 强刷即可）；
> 改了 `.py` **必须重启**（`Ctrl+C` 后重新 `python app.py`）。

## 五、报错对照表：出错时先看哪个函数

| 现象 | 先去看 |
|---|---|
| 页面 404 | `do_GET`（第 1010 行）的路由表，看这个网址有没有分支 |
| 后台一直跳回登录页 | `session_valid`（第 728 行）——Cookie 签名或过期问题 |
| 时间表状态不对 | `slot_status`（第 552 行）——5 个 `if` 的顺序 |
| 休息规则没生效 | `rule_covers`（第 528 行）——星期几算错了？跨午夜？生效日期？ |
| 格子数不对 | `DAYS_SHOWN`（第 54 行）和 `build_slots`（第 584 行） |
| 客户点预约报 400 | `api_book`（第 1234 行）——是把校验顺序改乱了？还是前端没传联系方式？ |
| 客户点预约报 409 | 那几格真的被占用了，`create_booking`（第 624 行）里会列出是哪几小时 |
| 客户点预约报 429 | 限流：同一个 IP 10 分钟最多 5 次（`book_rate_limited`，第 684 行） |
| 收不到预约通知 | 后台「安全与备份 → 预约通知」看上次失败原因；发送逻辑在 `send_notify`（第 774 行） |
| 老站点升级后报 no such column | `ensure_column`（第 170 行）没被 `init_db()` 调到 |
| 图片上传失败 | `save_data_url`（第 340 行）——格式/大小限制 |
| 上传成功但主页看不到 | 资料的 `visible` 是不是假的？`list_gallery`（第 313 行） |
| `database is locked` | 有地方忘了 `with _db_lock` |
| 部署后打不开 | 看 Render 的 Logs；确认 `PORT` 没写死（第 71 行） |
